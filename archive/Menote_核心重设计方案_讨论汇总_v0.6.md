# Menote 核心重设计方案（讨论汇总 v0.6）

- **整理日期**：2026-10-31
- **文档状态**：Menote V2 产品设计基线（讨论稿）；记录已达成的共识与建议的重启路线，**不是最终技术实施规格**
- **适用范围**：Menote V2 核心信息架构、Note/Memo 交互、加密边界、MCP Agent 接入、S3/WebDAV 远程备份、Cloudflare GitHub 一键部署约束、存储原则、后续扩展与重启迁移策略
- **说明**：已明确优先按 **Menote V2 重新启动产品与前端架构**；技术层执行“选择性继承”，不全量重写底层能力。独立 V2 仓库是推荐实施方式，具体仓库与迁移方案仍需实施阶段确认；本文不代表已修改仓库。
- **v0.2 更新**：增加固定加密主题与普通主题内单篇密码加密的完整产品规则；两者均纳入核心功能，不扩展为任意主题整体加密。
- **v0.3 更新**：增加通用表格的外部数据源接入方向：浏览器插件作为通用数据写入入口，Raindrop 作为可选双向同步连接器；支持同一张表同时接收两个入口、编辑后手动回写，并明确冲突与备份边界。此能力**确定为后期扩展**。
- **v0.4 更新**：确定 V2 以**产品与前端重启、底层选择性复用**为主路线；增加现有模块复用判断、V2 分阶段建设、旧数据迁移、安全隔离与交付判据。
- **v0.5 更新**：明确 **MCP（外部 AI Agent 查询、新增、编辑）**及**自动备份至 S3 兼容存储 / WebDAV**均为 V1 已存在、V2 **必须保留的核心平台能力**，而不是与 Raindrop 一同延后的第三方插件。补充权限、安全、远端备份与恢复验收基线。配套组件设计升至 v0.2。
- **v0.6 更新**：新增 Cloudflare GitHub 一键部署的正式产品验收标准：**用户仅需授权导入并设置一个 Worker Secret `AUTH_PEPPER`**；D1、R2、资源绑定、数据库初始化、Cron 和前后端部署都由项目配置与程序自动完成；明确 R2 账号级开通的必要例外及失败态。配套组件设计升至 v0.3。

## 一、核心定位与产品边界

Menote 以两种内容形态为基础：

| 形态 | 定位 | 主要使用方式 | 内容与存储原则 |
| --- | --- | --- | --- |
| **Memo** | 非正式、即时、轻量的随手记录 | 时间线浏览、快速录入、原位修改 | 数据库中的独立记录；正文保留 Markdown 表达能力 |
| **Note** | 正式、长期、可整理的文档 | 按主题组织、完整编辑、阅读与检索 | Markdown 是文档的规范内容格式，支持 YAML Frontmatter |

- **Memo 与 Note 保持边界**：todo 是 Memo 的辅助组织方式，不是第三种顶层内容；Note 的 YAML 即使带有 `status`，也不会自动进入 Memo 的 todo 面板。
- 以**记录、整理、检索与阅读**为核心，不把产品扩展成复杂项目管理、数据库自动化或工作流平台。
- **安全边界**：正式 Note 包含两种必要加密能力：系统固定的私人加密主题，以及普通主题内单篇密码加密；它们不是第三种内容形态。
- 支持从 Memo 整理或转为 Note 的方向，但保留原记录的具体策略、关联方式需在实施设计时确认。

## 二、信息架构与导航

### 2.1 正式笔记的组织结构

采用 **主题 → 分组 → 笔记**：

```text
收件箱（Inbox）             ← 独立的固定入口
私人空间（加密主题）        ← 固定系统主题，锁定/解锁整区

主题：游戏美术
├── 分组：UE5
│   ├── 材质工作流.md
│   └── 场景灯光规范.md（可单篇加密）
└── 分组：Houdini
    └── 程序化资产.md

主题：产品设计
├── Menote 设计.md          ← 可以直接放在主题下
└── 分组：交互研究
    └── 编辑器研究.md

Memo                         ← 独立时间线，不进入上述目录树
```

- **主题**：一级归属，强调内容围绕的长期方向。
- **分组**：主题内可选的整理层；不要求所有笔记必须有分组，**最多一层分组**，避免无限嵌套。
- **笔记**：正式内容对象；创建时无需先指定主题或分组，允许暂未分类。
- **标签**：用于跨主题检索与关联，不代替目录层级。
- **私人空间**：系统固定的加密主题，遵循同样的可选分组和笔记组织方式；普通主题中也允许单篇加密，但不支持“任意主题整体加密”。详见第五章。

### 2.2 固定收件箱

- **收件箱（Inbox）**是系统固定的暂存入口，与普通主题分开。
- 未来浏览器剪藏插件、Android App 等采集入口产生的**待整理收藏**统一进入收件箱。
- 收件箱负责“先收集，后整理”，不隐含自动过期或自动删除。
- 剪藏插件、Android App **属于后续规划**；当前先保留信息架构位置，不作为本轮核心实施前置条件。
- **收藏网址**与**剪藏网页正文**是不同动作：前者未来可直接写入用户指定的通用表格，后者进入收件箱待整理；二者不必绑定 Raindrop，也不等于额外开发一套书签系统。详见第七章。

### 2.3 侧边栏与视图

左侧导航顺序：

1. **Memo 快速输入框**。
2. **新建笔记**按钮。
3. 常用入口：**最近编辑 / 收藏**。
4. **主题与分组树**（含固定的「私人空间」加密主题）。

创建交互：

- **Memo**：默认单行输入；点击展开为多行，**占用“新建笔记”按钮所在的共享区域**，其余导航不被向下推，也不向右弹浮窗。保存后恢复原布局并留在当前页面；未完成草稿在收起时应保留。
- **Note**：点击“新建笔记”立即打开空白文档编辑页，**先写再分类**，不弹出必填归属表单。
- 两种创建态互斥，不需要同时展开。

正式笔记提供两种布局：

| 布局 | 结构 | 交互 |
| --- | --- | --- |
| **列表** | 左侧主题树 / 中间笔记列表 / 右侧文档 | 选中主题或分组后，中栏直接列出对应笔记，不在列表中重复制造层级 |
| **网格** | 左侧主题树 / 右侧笔记卡片网格 | 打开卡片进入独立文档阅读/编辑区域，并能返回网格 |

整体保留 Menote 简约、克制的视觉方向；不因架构整理而推翻全部既有设计语言。

## 三、Note：编辑器、属性与表格

### 3.1 编辑模式

- **默认：所见即所得编辑**，参考 Typora。标题、列表、引用、图片及表格呈现接近最终样式；在需要编辑具体语法的位置按需暴露 Markdown 标记。
- **仅保留两个常驻模式**：**编辑**与**预览**。预览模式以阅读为主，正文只读。
- 不保留“纯源码编辑”“即时渲染”“分屏”作为并列的日常模式。
- 必要的 **Markdown 源码查看/编辑**可作为“更多操作”中的高级入口，具体入口及行为尚待细化，不构成第三种常驻模式。

### 3.2 YAML：独立的内联属性区

文档内部自上而下为：**标题 → 属性区 → Markdown 正文**。

- YAML Frontmatter 保留在 `.md` 文档中，但默认**不显示为源码块**。
- 属性区使用与正文有明确视觉分离的轻量布局，默认显示为经过排版的属性值，**不是满屏输入框**。
- **点击值直接编辑**：文本直接输入、日期弹出日期选择、单选/多选直接选择、布尔值直接切换等。
- 属性区可折叠；空文档不铺设大量空字段。
- **即使正文处于预览模式，属性区仍允许独立编辑**；写回需经统一文档更新链路，避免与正文自动保存冲突。
- 支持自定义属性类型、外来 YAML 键与未知值原样保留；属性的**显示名只影响 Menote UI，不改变 Markdown 中的原始键名**。
- YAML 解析与写回应保持往返兼容；不因为类型控件无法识别值就擅自清空、覆盖或丢弃数据。

### 3.3 Markdown 表格

**表格始终以标准 Markdown 表格为内容载体，结构化能力只增强编辑体验。**

- 编辑时提供类似飞书多维表格的**单元格编辑与字段类型控件**；预览时显示普通 Markdown 表格。
- 计划支持常用字段类型：文本、数字、日期、单选、多选、布尔/复选框、链接等；字段类型定义可利用 YAML 元数据，尽量复用 Note 属性编辑器的控件与规则。
- 没有字段定义的普通 Markdown 表格仍应可编辑；类型定义是增强信息，**不是打开表格的前提**。
- 明确**不做复杂公式、自动化、跨表关系或数据库式工作流**。目标是简单好用的记录清单。
- 自定义字段的序列化必须保持普通 Markdown 阅读器可读；多选分隔、特殊字符和换行的写回契约**仍需单独确认**。
- 表格是独立的 `.md` 文档形态，还是普通 Note 内的表格视图/编辑区，**实现边界待细化**；不能为了编辑器方便而改变 Markdown 作为内容载体的原则。
- **外部数据接入不改变此原则**：表格仍是通用 Markdown 表格，第三方连接器只负责数据读取、字段映射、写入和回传；不能把表格变成 Raindrop 专属内容类型。

## 四、Memo：时间线、todo 与图片浏览

### 4.1 基础交互

- **时间线是 Memo 默认视图**；Memo 轻量、原位编辑，支持必要的 Markdown 样式，不打开完整 Note 编辑器。
- 内容修改、标签与图片均依附于原 Memo 记录；Memo 不强制出现 YAML 属性区。
- Memo 的标签属于内容分类；**todo 状态是独立的结构化字段，不用 `#doing` 之类的标签承担状态语义**。

### 4.2 todo：Memo 内的侧边面板

todo **不再拥有独立完整页面**，仅在 **Memo** 视图旁作为可展开/折叠、且不遮挡时间线的辅助面板出现；不延伸到正式 Note 阅读区。

todo 只有**一个互斥状态字段**，分为三个组：

| 分组 | 状态值 | 行为 |
| --- | --- | --- |
| 待办 | `todo` | 新任务的默认位置 |
| 进行中 | `doing` | 将任务拖入此组即更新状态，可拖回“待办” |
| 已完成 | `done` | 在任何未完成组勾选任务，即自动进入已完成 |

固定交互：

- **拖拽到其他分组** = 修改状态；不增加“进行中开关”等第二维度。
- **勾选** = 完成并移到“已完成”；取消完成 = 回到“待办”。
- 三个标题只是面板里的**界面分组**，**不写入 Memo 正文**。
- 不再使用三段流程的强制推进按钮，也不需要另设状态下拉框。
- 普通 Memo 没有任务状态；转为 todo 时设置 `todo`；移除 todo 属性后恢复普通 Memo。
- 已完成分组可默认折叠，节省面板空间。

### 4.3 图片瀑布流（非当前必做）

- 基于**同一批 Memo 数据及其图片附件**，增加图片筛选/瀑布流浏览；**不是独立图库内容类型**。
- 每张图片可独立成卡片，一条 Memo 的多张图片均可出现；点击图片查看大图，并可定位到来源 Memo。
- 复用日期、标签筛选；优先缩略图与懒加载，注意大量图片的滚动和内存性能。
- **明确延期**：作为后续体验扩展，不阻断当前核心架构的完成。

## 五、加密：固定私人主题与单篇密码保护（核心功能）

### 5.1 两种作用域，不增加第三种

| 能力 | 固定加密主题「私人空间」 | 普通主题内的单篇加密 |
| --- | --- | --- |
| 主要用途 | 生活记录等不希望他人查看的私人资料 | 工作或其他普通主题中个别需要保护的内容 |
| 归属 | 系统固定的唯一加密主题，可包含分组和多篇 Note | **留在原主题/分组**，不因加密而搬走 |
| 解锁方式 | 主题级「锁定 / 解锁」；解锁一次可访问本区全部内容 | **打开该篇时输入密码**；仅解锁当前笔记 |
| 锁定范围 | 统一锁定该加密主题的内容 | 仅锁定选中的笔记，不影响其他内容 |
| 界面状态 | 主题上明确的锁定/解锁状态和手动锁定入口 | 单篇笔记有锁标识与密码输入界面 |
| 是否为当前核心 | **是** | **是** |

**确定不做**：允许任意普通主题一键整体加密；也不因单篇加密而创建其他特殊内容类型。Memo 不进入固定私人主题；本轮加密设计对象为正式 Note。

### 5.2 交互与状态

- **私人空间**：锁定时不能读取其中的正文和附件；解锁后，该主题里的笔记按普通 Note 的方式浏览与编辑；用户可以随时执行「锁定」。建议新会话默认锁定，具体超时锁定策略待技术设计。
- **单篇加密**：普通主题中的受保护笔记保留原位置；点开后显示密码输入，验证成功后才展示正文并允许正常编辑。默认离开该笔记后重新锁定（具体如何处理编辑中的未保存改动需在实现时保证安全）。
- 两种解锁**作用域相互隔离**：解锁私人空间不能解锁工作主题的单篇加密笔记；解锁单篇也不能解锁私人空间。
- **解锁不等于分享**：向同事展示或分享某一篇内容，不得顺带暴露其他笔记或整个私人主题。分享链接/授权机制应独立设计，不因本机解锁而自动放宽服务端访问控制；是否支持加密笔记的直接在线共享待后续确定。

### 5.3 数据安全的最低要求

- “密码保护”必须是**真实的内容加密**，不能仅靠 UI 隐藏或一个前端密码框。未经授权不能通过接口直接获取正文、附件明文。
- 加密正文及相关附件；缩略图、索引、检索摘要、缓存、历史版本和备份是否泄漏敏感内容，需要按同一安全边界处理。普通主题的单篇加密至少不能泄露其正文内容；标题等元数据的可见范围需明确约定。
- 可复用底层加解密组件，但**主题密钥作用域**和**单篇密码的授权作用域**不能混为一体；不以“加密整个主题成为一个大文件”为目标，避免影响单篇修改和同步。
- 必须明确密码修改、遗失/恢复（若无恢复能力需明确提示）、离线访问、换设备解锁与备份恢复的行为，具体密码派生、密钥包装、加密算法和数据迁移由技术方案确定。

## 六、数据存储、同步与导出

### 6.1 记录粒度 ≠ 物理文件粒度

**不采用“一条 Memo 对应一个物理文件”的运行时模型。**

- **Memo**：数据库中每条 Memo 有独立 ID 和记录；正文为 **Markdown 字符串**，创建时间、修改时间、标签、todo 状态等采用结构化字段。按记录插入、更新、查询，不需要为了修改一条 Memo 重写整个月份的 JSON 文件。
- **Note**：Markdown（含 YAML）是规范文档内容；数据库可管理文档索引、归属、版本与同步，但不改变 Markdown 的可移植性。
- 可沿用或重组现有 **IndexedDB（本地）+ Cloudflare D1（云端）** 的持久化与同步能力；具体表结构与事务、冲突策略属于技术设计。
- **JSON 是结构化数据表达方式，不等于必须将每个月的数据实时存成一个 `.json` 文件**。

Memo 逻辑记录示例（仅示意数据模型，不是最终数据库表结构）：

```json
{
  "id": "memo_001",
  "content": "今天整理了 **Menote** 的交互方案。",
  "createdAt": "2026-10-31T08:00:00Z",
  "updatedAt": "2026-10-31T08:00:00Z",
  "tags": ["Menote", "设计"],
  "status": "doing"
}
```

普通 Memo 的 `status` 为 `null` 或不设置。`todo / doing / done` 只用于 Memo 的任务辅助视图，不与 Note 属性的同名字段混淆。

### 6.2 备份与导出

- **JSON**：优先作为完整恢复所需的结构化备份载体，保留记录 ID、时间、状态、关联和必要版本信息。
- **Markdown**：作为通用、可迁移的内容导出格式；Memo 导出时按约定生成 YAML + Markdown，Note 尽量保持原始 `.md` 内容。
- **按时间段组织 Memo 备份**（例如每月一个分片），而不是一条 Memo 输出一个备份文件；具体按月/按年、快照与增量策略待定。
- 定期备份需覆盖**历史记录在后续月份被编辑或删除**的情况，不能只备份“本月新增”。
- 附件需要随备份/导出具备可恢复的引用与对应文件，完整方案待技术设计。
- **远程备份是核心需求**：支持将完整可恢复的数据快照持续备份至 **S3 兼容存储**与 **WebDAV**，可配置目标、凭据、调度与手动执行；详见第十一章。
- **区分两条链路**：本地下载 JSON/Markdown 文件服务于导出与迁移；远端备份服务于持续灾难恢复，不能把“导出成功”替代“远端备份可恢复”。

## 七、外部数据源与浏览器收藏（后期扩展）

### 7.1 定位与范围

- **已确定方向，非当前必做**：不重新开发 DogEar 式的独立书签系统；利用 Menote 的**通用 Markdown 表格编辑能力**管理外部结构化记录。
- **连接器是数据中间件**：接入第三方 API，映射到指定表格的字段，支持用户手动**下载 / 上传**，而不是定制一套 Raindrop 专属表格或管理界面。
- **首个验证对象为 Raindrop**：当前已有约 **414 条书签**，希望改善浏览体验、在表格内编辑，并建立独立备份。数量是本轮评估时的现状，不是产品限制。
- 先验证单个适配器，再决定是否抽象为通用插件 SDK；本轮**不要求提前建设完整插件生态**。

### 7.2 三层职责与两种写入入口

```text
浏览器扩展（未来）                      Raindrop 连接器（未来）
  ├─ 收藏网址 → 指定通用表格              ├─ 读取 Raindrop 收藏夹 / 书签
  └─ 剪藏网页 → 收件箱                    ├─ 字段映射 / 外部 ID 关联
                                       └─ 比对 / 上传 / 下载
             │                                  │
             └──────────────┬───────────────────┘
                            ▼
                 Menote 通用 Markdown 表格
                  阅读 / 筛选 / 字段编辑
                            │
                     手动确认同步
                            ▼
                       Raindrop
```

- **浏览器扩展**是通用内容录入入口：用户选择“收藏网址”时，只提取 URL、标题、必要说明/标签等，写入**用户指定或预设为默认收藏目标的通用表格**；不要求安装 Raindrop 连接器。
- **剪藏网页**是另一种录入动作：保存实际网页内容，进入**收件箱**供后续整理；用户可以在需要时选择只收藏地址，或分别执行收藏与剪藏。
- **Raindrop 连接器**是外部系统同步适配器：绑定某张表与指定账号/收藏范围后，负责**拉取远端、字段映射、差异比对和回写远端**，不直接定义新的笔记内容类型。
- **同一张表可以接受多个写入入口**：Raindrop 下载的历史书签，以及浏览器扩展新增的本地书签，都进入该表的统一编辑界面；本地新行在同步时可创建为新的 Raindrop 书签。
- **表格不依赖连接器存续**：断开 Raindrop 后，本地表格及内容仍可保留、阅读与编辑；连接器不应成为唯一访问这些书签的方式。

### 7.3 绑定与数据匹配

- 每一行拥有**稳定的 Menote 本地行 ID**；已关联远端的行另维护 **Raindrop 记录 ID**。二者不能互相替代；仅凭 URL 不足以保证可靠匹配。
- 建议将外部账户/收藏范围、字段映射、远端 ID、上次同步版本/时间、变更状态等**连接器技术元数据放在数据库中**，通过表格与行 ID 建立关联；不要求把这些内部状态逐列写入可移植的 Markdown 表格。
- 表格中的通用列可映射标题、网址、标签、描述、收藏夹等；某些第三方字段不可编辑或无法回写时应明确标识，不能虚假承诺全字段双向修改。
- 两种入口对已有网址可能产生重复记录：优先依据远端 ID 匹配已同步行；遇到相同 URL 时可提示用户确认合并，**不自动将“同网址”当成同一书签**。

### 7.4 最小双向同步流程

1. **绑定**：用户指定一张表，选择 Raindrop 账号与同步范围，确认字段映射。
2. **下载**：分页拉取远程书签；有已知远端 ID 的更新已绑定行，未知的新增行；先检查本地未上传改动。
3. **本地编辑**：Menote 表格可编辑标题、链接、标签、描述等通用字段；浏览器扩展也可向表格新增书签。
4. **预览差异**：展示将新建、将更新、需人工处理冲突的记录；本地和远端同时更改同一字段时，不静默覆盖。
5. **确认上传**：未绑定远端 ID 的新行调用创建操作；已绑定且确有变更的行调用更新操作；成功后保存返回的远端 ID 与同步基线。

**边界规则**：首版采用**手动上传/下载**，不做实时自动双向同步；本地删除表格行**默认不触发远端删除**，如未来提供远端删除必须另行确认；防止双端反复覆盖、意外重复创建或将本地错误传播至云端。

### 7.5 备份与规模

- Raindrop 同步**不等于备份**。需要独立的书签数据快照：优先 JSON 保留原始 ID、时间、收藏夹、标签及必要的源字段；Markdown/HTML 等作为可读、可迁移的导出选项。
- 同步后的表格也应能在脱离 Raindrop 的情况下浏览；但**一份可能被持续改写的表格不是历史版本备份的替代品**。
- 以当前约 414 条书签为起点，可先验证单表方案；若未来数据量显著增长，再评估表格大小、全文写回、增量同步与按收藏夹拆表，**不提前扩大核心表格系统的复杂度**。

### 7.6 分阶段安排（不阻断核心开发）

1. **只读验证**：连接 Raindrop、下载到指定表格、检查字段映射及浏览体验、生成独立备份。
2. **可编辑同步**：加入手动上传/下载、远端 ID 对应、差异预览与冲突保护。
3. **浏览器采集**：提供“收藏网址 → 绑定表格”与“剪藏正文 → 收件箱”两个并列入口，收藏网址不依赖 Raindrop。

> 已确认的是上述产品机制与职责边界；插件实现载体（内置适配器、独立插件、扩展 API）、授权方式、同步元数据表结构与具体交互样式，仍属于后续技术设计。

## 八、阶段划分

### 当前优先：核心闭环

1. 明确并稳定 **Memo / Note 双内容形态**及信息架构。

7. **按 V2 重启路线实施**：产品/前端重新搭建，旧版保持稳定，已有基础设施逐项审查后复用；具体实施参见第十章。

- Memo 图片瀑布流及图片筛选的体验完善。
- 浏览器剪藏插件、Android App，以及接入固定收件箱的采集工作流。
- **通用表格的外部数据连接器**：以 Raindrop 为首个验证对象，完成手动下载/上传与独立备份；浏览器扩展可将网址收藏直接写入指定表格，并保持剪藏正文进入收件箱的独立动作。详见第七章。
- 更复杂的内容组织、扩展能力与高级交互；不预先引入公式、自动化等非目标功能。

**最终原则**：**Memo 是数据库中的轻量记录，Note 是以 Markdown 为规范格式的正式文档；两者共享必要的 Markdown 表达能力，但不强制共享存储模型或完整编辑界面。** 安全保护是 Note 的权限与加密能力：**一个固定私人加密主题 + 普通主题内的单篇密码加密**，不制造第三种内容形态。一切附加视图（todo、瀑布流）、收集入口（Inbox、剪藏、Android）都依附于两个核心内容形态。**外部数据连接器属于通用表格的可选扩展**：浏览器收藏能直接写表，Raindrop 中间件负责拉取与回写，不建立第二套书签内容系统。


## 十、Menote V2 重启路线与技术资产复用（v0.4 新增）

### 10.1 重启的准确含义

**方向已确认**：按照 V2 的产品设计重建信息架构、前端页面与核心交互，避免继续在旧版多功能视图上逐个做删改；**不等于所有代码从零写**。

- 旧 Menote 保留为稳定版本与历史数据来源；V2 应在独立的开发环境中实现和验证，**不得直接对生产 D1/R2/生产数据做试验性迁移**。
- **推荐独立 V2 仓库**以避免旧版 `AGENTS.md`、`DESIGN.md`、`wiki/` 的历史设计约束反向影响新产品；也可先建立专用重构分支做技术验证。最终仓库组织、名称与部署域名属于实施决策，尚未强制确定。
- 技术栈原则上沿用 **React + TypeScript + Cloudflare Workers + D1 + R2 + 本地 IndexedDB**，除非评估证明替换存在显著收益。编辑器底座需要单独选型或 PoC，不因为旧版用了 CodeMirror 就自动锁定。
- 先确立 V2 数据契约，再决定旧模块“直接复用、适配、仅借鉴还是淘汰”；**禁止为迁就旧 YAML / 旧同步协议而损害新 Memo 的结构化存储设计**。

### 10.2 旧模块处理建议

以下为**代码勘查后的初步分类，不是未经验证的直接复制清单**：

| --- | --- | --- |

| Note 工作区、编辑器模式、属性面板 | **重建交互与组合关系** | 两模式 Typora 式编辑、内联 YAML 属性区与旧侧轨/多模式结构不同；先验证编辑器技术选型 |

### 10.3 分阶段实施（按闭环推进，避免旧里程碑完整搬家）

**V2-A：架构骨架与核心数据**

- 建立新的产品文档、`AGENTS.md` 与视觉规范；定义 Memo、Note、主题、分组、收件箱、附件和 todo 的统一契约。
- 搭建两种正式笔记布局、主题树与基本路由；Memo 快速录入及时间线可用；先使用隔离测试数据。
- 选出 WYSIWYG 编辑器底座并完成 Markdown 往返验证，避免后期才发现结构不兼容。

**V2-B：内容交互闭环**

- Note：编辑/预览两模式、文档顶部内联属性区、普通 Markdown 表格的结构化编辑。
- Memo：简化 Markdown 编辑、任务三组侧栏、拖拽与勾选更新状态。
- 基础搜索、主题归档、收件箱入口、异常状态与可访问键盘操作。

**V2-C：生产级能力接入**

- 接入认证、设备本地数据、增量同步、附件、版本历史、回收站、**MCP Agent API** 与 **S3/WebDAV 远程定时备份**。
- 固定加密主题及单篇密码加密，验证锁定内容的网络、本地缓存、缩略图、历史与备份边界。
- 数据模型与同步协议如有变化，按版本化迁移执行；先验证功能正确性，再整合真实数据。
- 在隔离环境实测外部 MCP Agent 的查询/新增/编辑、令牌撤销和权限阻断；分别实测 WebDAV 与 S3 的推送、故障续传及远端恢复。

**V2-D：旧数据迁移与替换**

- 从旧 Menote 导出完整备份，建立旧 → 新的数据映射与迁移报告。
- 检查正文、YAML、主题路径、附件引用、任务状态、加密条目、版本及关联 ID 的一致性；对无法无损转移的字段给明确报告。
- 使用隔离 D1/R2 完成恢复与往返测试；确保旧版本仍可访问，并保留回滚窗口。**验证完成前不得以 V2 覆盖旧版数据。**

### 10.4 必须优先验证的技术风险

1. **Typora 式编辑器 Markdown 往返**：不能因可视化编辑损坏 YAML、GFM 表格、代码块、附件引用及不认识的 Markdown 内容。
2. **Memo 数据契约的变化**：新结构化字段与旧 YAML 派生字段如何迁移、同步及导出，需要唯一权威来源；不可长期双向维护两份互相覆盖的状态。
3. **加密兼容**：主题锁与单篇密码不共享解锁授权；验证旧格式解密/新格式封装、密码错误、换设备、离线访问与备份恢复。
4. **同步冲突和离线编辑**：并发保存、重复提交、删除恢复、跨设备冲突不能静默丢失记录。
5. **MCP 安全边界**：外部 Agent 的授权范围、只读/写入权限、重复提交与编辑冲突必须有服务端保障，不得读取私人主题或单篇加密笔记明文。
6. **远端备份恢复性**：不能只测试上传成功；应验证加密备份、附件一致性、密钥恢复、完整重建与断点续传。
7. **范围控制**：不要把后期剪藏、Raindrop 连接器和 Android App 提前加入 V2 核心交付范围。

### 10.5 交付与推进原则

- **优先完整闭环，不为非关键单项反复打磨而卡住后续模块**。记录未达理想的体验问题并分级，核心数据正确性、安全和不可恢复的数据丢失仍为必须解决的阻断项。
- 每阶段要求可运行、可操作和最小自动化回归；视觉细节逐步收敛，不以“绝对完美”作为进入下一阶段的门槛。
- 任何生产数据迁移、密钥/认证策略修改、第三方授权与分享策略，必须独立审查，不因产品重启自动放宽安全要求。
- 组件与交互细节详见配套文档 **《Menote V2 组件与交互详细设计 v0.2》**；仍有待定部分不应自行猜测为产品定稿。


## 十一、V1 既有平台能力：MCP 与 S3/WebDAV 远程备份（v0.5 补充）

> **范围定性 `[已定]`**：以下两项不是新提出的实验功能，而是 **V1 已经开发、V2 必须保留的核心能力**。它们与第七章的 Raindrop / 浏览器插件不同：**MCP 是对外 AI Agent 读写接口；S3/WebDAV 是用户数据的持续备份渠道**，均须在 V2 迁移上线前完成可操作验证。下列技术细节以 V1 实现作参考，V2 最终接口可随数据契约调整。

### 11.1 MCP：让其他 AI Agent 安全访问 Menote

- **外部调用方**：Cursor、Claude Code、Codex 及其他支持 MCP 的 Agent，通过网络连接 Menote，不要求打开 Menote 网页，也不属于 Raindrop 插件的一部分。
- **至少保留的能力**：查找内容、列出主题/分组和条目、读取正文与历史；创建 Memo/Note、追加内容、编辑 Note/Memo、更新表格行、调整内容归属、移入回收站。V1 已有 **5 个读工具 + 6 个写工具**，V2 优先适配而非随意扩大权限。
- **安全边界**：使用独立 MCP 访问令牌；可设置权限、可访问范围、是否包含 Memo、有效期、撤销；由服务端执行所有权限判断。**私人加密主题与单篇加密 Note 默认完全不暴露给 MCP**，无论用户是否在浏览器中解锁。
- **写入正确性**：Agent 的新增/编辑必须走与 UI 相同的业务命令与数据验证路径；采用版本前置条件/冲突检测和重复操作去重，避免覆盖用户的新改动；变更进入正常同步、历史和审计流程。
- **边界不扩大**：MCP 不是无权限的通用远程控制通道；备份配置、令牌机密、分享管理、加密密钥、永久删除不作为默认可调用工具。
- **V2 适配重点**：主题/分组替换旧文件夹层级、todo 变为 Memo 结构化 `status`、表格继续以 Markdown 为规范格式；这些变动可能影响工具参数、检索结果、权限范围与版本号。应提供兼容迁移策略，不直接声称 V1 的 11 个工具无需修改即可运行。

V1 参考实现：[MCP 工具注册表](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/services/mcp/registry.ts)、[令牌契约](https://github.com/maxxie6418/Menote/blob/main/packages/shared/src/mcp.ts)、[可见范围过滤](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/services/mcp/scope.ts)。

### 11.2 远程备份：S3 / WebDAV 是核心灾难恢复能力

- **备份目标**：可配置至少一个 **WebDAV 目录**或 **S3 兼容对象存储**，支持多个目标独立启停；目标可单独设置连接参数、目标名称与凭据。
- **执行方式**：提供手动「推送一次」及可配置的定时推送。V1 已支持 `daily / weekly` 档位；V2 应优先继承这一简单口径，不先引入复杂调度平台。
- **数据内容**：远端备份需覆盖 Note、Memo 结构化字段、主题/分组关系、附件及必要恢复元数据。已删除/历史修改内容是否归档、快照怎样分片，应由 V2 备份格式明确，不可遗漏老月份的变更。
- **安全**：备份凭据加密保存且不可从设置 API 回显；出站备份和附件涉及的加密数据应维持必要的机密性与可恢复性。不得将用户主密码或明文密钥直接写进远端备份。
- **远端删除策略**：参考 V1 的 `append_only`（默认保留远端内容）与 `sync`（同步删除）两种策略；任何可能破坏远端可恢复历史的数据清理，应有显著说明与确认。
- **运行状态**：显示最后执行时间、成功/部分成功/失败、剩余待推送内容与可理解的失败原因；部分失败可继续，不把一次成功请求当作完整备份已完成。
- **恢复**：必须定义并验证“从远端取回备份 → 校验清单与内容 → 取得必要解密凭据 → 在干净环境恢复”的完整演练。**V1 具备远端推送不等于 V2 已具备完整远端恢复 UI**；恢复路径需单独检查与补齐。

V1 参考实现：[备份目标数据契约](https://github.com/maxxie6418/Menote/blob/main/packages/shared/src/backup-targets.ts)、[远端备份推送状态机](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/jobs/push.ts)、[WebDAV 适配器](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/adapters/webdav.ts)、[S3 适配器](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/adapters/s3.ts)。

### 11.3 与 V2 其他模块的关系

| 模块 | MCP Agent 接入 | S3/WebDAV 备份 |
| --- | --- | --- |
| Note / Memo | 受限读写，遵守新数据契约与同步版本 | 保留完整记录和恢复所需元数据 |
| 通用 Markdown 表格 | Agent 可更新指定行，走统一表格写入命令 | 保存标准 Markdown 与必要字段定义 |
| 主题 / 分组 | 令牌仅可访问授权组织范围 | 恢复组织结构，不因迁移丢失归属 |
| 私人加密主题 / 单篇密码 | 默认完全不可见、不可读取、不可修改 | 保留密文、密钥包装及恢复所需信息，不输出明文 |
| 搜索 / 历史 / 回收站 | 权限过滤、操作审计、避免重复写入 | 遵循备份范围与保留策略，恢复后可验证 |
| Raindrop 连接器 `[后期]` | 独立能力，不依赖 MCP 工具命名 | 第三方缓存与绑定元数据是否备份需后续明确 |

### 11.4 V2 验收底线

1. 有效只读令牌可以查询和读取非加密 Note/Memo；写入被拒。有效写入令牌可以创建、编辑指定范围内容，并在 UI 和其他设备看到一致结果。
2. 对已撤销/过期/越权令牌，服务端拒绝访问；**私人加密主题、单篇加密 Note 在浏览器解锁后仍不能通过 MCP 被读取**。
3. 两次重复写入不应制造多份记录；版本不一致时返回可处理的冲突而非静默覆盖。写类工具保留审计记录。
4. 在测试目标中分别完成 **WebDAV 与 S3** 的连接验证、手动上传、计划推送、网络失败续传、远端内容完整性检查。
5. 在空白测试环境执行至少一次**从远端备份恢复**，验证 Memo 结构化状态、Note Markdown/YAML、附件、主题归属和加密内容可恢复；不以“文件已上传”代替恢复验收。
6. 新版上线前，旧版 MCP 工具与外部备份目标/凭据的迁移兼容性必须给出明确结果；不能自动迁移的项目需提供清晰的重新授权/配置指引。

## 十二、Cloudflare GitHub 一键部署与零附加配置（v0.6 新增）

### 12.1 产品级硬性要求 `[已定]`

> **Menote V2 必须支持从 GitHub 一键导入 Cloudflare 并完成部署。用户在首次部署期间，除在 Cloudflare 环境中设置一个密钥之外，不需要创建资源、修改配置文件、添加环境变量或手动接线。**

- **部署入口**：项目仓库提供 **Deploy to Cloudflare** 一键部署按钮；同时支持从 Cloudflare Dashboard 的 Workers & Pages 选择 GitHub 仓库导入。用户完成 Cloudflare/GitHub 账号授权并选择项目即可走默认流程，无须本地安装 Node、Wrangler 或执行终端命令。
- **唯一必填部署 Secret**：沿用 V1 的 `AUTH_PEPPER`，由用户在 Cloudflare Worker 的 Secret 管理中设置。它属于部署时的**唯一应用级人工配置项**，不提交到 GitHub，不作为公开 `vars`，不通过构建日志、页面或错误信息回显。后续单篇笔记密码、用户登录密码属于应用业务数据，不算额外的部署环境变量。
- **自动资源**：由项目预置的 Wrangler 配置触发 Cloudflare 原生 D1 数据库、R2 对象桶的自动创建和 Worker 绑定；不能要求用户手动查 `database_id`、输入 `account_id`、建立 Bucket 或复制资源 ID。应用依赖的 Static Assets、Worker API、Cron Triggers 也必须随项目交付配置就绪。
- **自动初始化**：首次启动通过可重入（幂等）的 schema 初始化/迁移完成 D1 表、索引及必要默认数据；不要求用户登录 Cloudflare 手动执行 SQL。部署脚本/运行时应具备迁移版本记录、失败停止或受控重试机制，禁止误把新旧 schema 混用。**资源自动创建是 Cloudflare 的能力，数据库 schema 自动迁移必须由 Menote 自己负责实现。**
- **自动持续部署**：Workers Builds 绑定 GitHub 主分支，后续 push 自动构建并部署；构建参数、工作目录、依赖安装/锁文件、产物路径、运行时兼容、静态资源路由均在仓库中确定，不能依赖用户手调 Cloudflare 构建命令。
- **默认可访问**：使用 Cloudflare 分配的 `*.workers.dev` 地址即可进入首次创建账号/初始化引导。自定义域名、独立 MCP 域名或其他高级网络配置均为可选项，不得作为首发可用性的前置条件。
- **配置自检**：启动时检测 `AUTH_PEPPER`、D1、R2、schema 版本与关键绑定；缺少 Secret 时必须拒绝敏感功能的正常工作，以清晰、可操作的错误指引完成**唯一必需配置**，绝不能静默降级成无密钥的生产环境；缺资源/迁移失败不能显示“部署成功可用”。

### 12.2 用户最短部署路径（成功口径）

```text
GitHub 仓库 → Deploy to Cloudflare / Cloudflare 选择仓库 → 授权导入
    ↓  项目自动安装依赖、构建、创建 Worker + D1 + R2 并完成绑定
    ↓  项目自动初始化/迁移 D1，部署静态资源和 API，配置 Cron
Cloudflare 环境 → 只填写一个 Secret：AUTH_PEPPER
    ↓
打开 workers.dev → 注册/初始化 → 新建 Memo/Note、附件上传可用
    ↓
后续 GitHub 更新 → Workers Builds 自动部署与安全升级
```

- **不得出现的必需人工步骤**：手动建 D1、手动建 R2 桶、手动配置数据库 ID/桶名/Binding、执行迁移 SQL、补第二个部署密钥、修改 `wrangler.jsonc`、写 GitHub Actions Secret、配置域名/DNS、启用额外付费服务才能让应用核心功能运行（Cloudflare 平台固有的服务开通例外除外）。
- **外部备份功能不等于部署配置**：使用 S3/WebDAV 远端备份时，用户需要在 Menote **应用设置页面**填目标地址和该存储服务的访问凭据。这属于用户主动启用外部服务的业务设置，**不要求写 Cloudflare 环境变量，也不阻断 Menote 初次部署**。Raindrop 同理，属于后期连接器授权。

### 12.3 平台前置条件与容错（不能混淆为产品配置）

- 用户必须拥有 Cloudflare 账号并授权连接 GitHub；这是平台身份和操作授权，不是 Menote 的额外配置。
- **R2 账号级启用例外**：截至本设计核验日，Cloudflare 的 R2 入门文档仍要求账号具有 R2 subscription；没有启用 R2 的账号可能需要完成一次平台服务开通流程。项目应明确提示此限制并尽量在导入时检测，**不可承诺绕过平台结算/服务授权**，也不应让用户随后手动建桶或绑 Worker。
- 如果 Cloudflare 账号权限、计划限制、R2 未启用或自动资源预配失败，应明确报错并指出所需的账号级操作，不能无限重试、创建多份同名资源，也不能把失败伪装成已完成部署。
- 生产、预览及迁移测试环境的数据库/桶必须隔离；不能因为 Preview 构建而写入或清理生产数据。重复部署应重用已有绑定，升级不可重新创建孤立的新 D1/R2。
- `AUTH_PEPPER` 的遗失/轮换涉及现有加密封装和认证的安全迁移。除非完成兼容的密钥轮换设计，**不得用重置 Secret 作为普通故障恢复手段**。

### 12.4 验收标准与优先级

**优先级：P1，首个正式 V2 发布前必过；首个可部署的开发预览阶段就要验证最小导入路径。**

1. 使用全新 Cloudflare 账号或隔离的测试账号，从 GitHub 仓库一键导入；不预先创建 D1/R2，不修改 Wrangler、构建命令及资源 ID，证明自动创建与绑定成功。
2. 仅设置 `AUTH_PEPPER` 一项应用级部署 Secret，即可完成首次账号初始化、Memo/Note 保存、附件写入/读取、浏览器刷新后的数据保持；未设 Secret 时必须安全拒绝并说明处理方式。
3. 数据库初装与升级迁移完全自动、幂等；重复部署不丢现有数据、不重复建资源；失败后有清晰的诊断与恢复路径。
4. 提交一次 GitHub 更新，证明 Workers Builds 自动部署且不覆盖唯一 Secret、D1/R2 绑定、备份计划或现有数据。
5. 定时触发机制、MCP 入口、S3/WebDAV *功能入口*可用；后两者实际访问外部服务时才由用户按功能授权/配置，不能强制成为部署前置步骤。
6. 若账号尚未开通 R2 或缺少资源创建权限，部署引导应明确说明**平台前置限制**并阻止错误的“已就绪”判断；不要求为此补充其他应用环境变量。
