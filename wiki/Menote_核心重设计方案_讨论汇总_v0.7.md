## 一、核心定位与产品边界

Menote 以两种内容形态为基础：

| 形态 | 定位 | 主要使用方式 | 内容与存储原则 |
| --- | --- | --- | --- |
| **Memo** | 非正式、即时、轻量的随手记录 | 时间线浏览、快速录入、原位修改 | 数据库中的独立记录；正文保留 Markdown 表达能力 |
| **Note** | 正式、长期、可整理的文档 | 按主题组织、完整编辑、阅读与检索 | Markdown 是文档的规范内容格式，支持 YAML Frontmatter |

- **Memo 与 Note 保持边界**：todo 是 Memo 的辅助组织方式，不是第三种顶层内容；Note 的 YAML 即使带有 `status`，也不会自动进入 Memo 的 todo 面板。
- 以**记录、整理、检索与阅读**为核心，不把产品扩展成复杂项目管理、数据库自动化或工作流平台。
- **安全边界**：正式 Note 包含两种必要加密能力：系统固定的私人加密主题，以及普通主题内单篇密码加密；它们不是第三种内容形态。
- **多用户（第十一批）**：默认单用户使用；可开启注册（开关与期限由 owner 控制），多用户之间数据**完全独立、互不可见、互不共享**（内容、附件、令牌、审计、备份目标均按用户隔离）；首版不提供跨用户协作或共享。
- 支持从 Memo 整理或转为 Note 的方向，但保留原记录的具体策略、关联方式需在实施设计时确认。

## 二、信息架构与导航

### 2.1 正式笔记的组织结构

采用 **主题 → 分组 → 笔记**：

```text
收件箱（Inbox）             ← 固定入口：外部采集与 AI Agent 输入待整理
草稿箱（Drafts）            ← 固定入口：自建未归类笔记队列
私人空间（加密主题）        ← 固定系统主题，锁定/解锁整区

主题：游戏美术
├── 分组：UE5
│   ├── 材质工作流.md
│   └── 场景灯光规范.md（可单篇加密）
└── 分组：Houdini
    └── 程序化资产.md

主题：产品设计
├── Menote 设计.md          ← 可以直接放在主题下
└── 分组：交互研究
    └── 编辑器研究.md

Memo                         ← 独立时间线，不进入上述目录树
```

- **主题**：一级归属，强调内容围绕的长期方向。
- **分组**：主题内可选的整理层；不要求所有笔记必须有分组，**最多一层分组**，避免无限嵌套。
- **笔记**：正式内容对象；创建时无需先指定主题或分组，允许暂未分类。
- **标签**：用于跨主题检索与关联，不代替目录层级。
- **私人空间**：系统固定的加密主题，遵循同样的可选分组和笔记组织方式；普通主题中也允许单篇加密，但不支持“任意主题整体加密”。详见第五章。
- 上图表达的是**内容归属结构**，不是左侧目录的显示形态：左侧目录树只显示主题与分组、不显示笔记（显示规则见 2.3）。

### 2.2 收件箱与草稿箱（双固定入口，v0.7 定稿）

- **收件箱（Inbox）**：外部内容的进站口——未来浏览器剪藏插件、Android App 的采集内容，以及 **AI Agent 新建的 Note**，统一进入收件箱待用户整理确认；与普通主题分开。
- **草稿箱（Drafts）**：用户自己新建、尚未指定主题的 Note 队列；「先写再分类」的笔记在归类前出现在草稿箱。
- 两个入口都遵循“先收集，后整理”，不隐含自动过期或自动删除。
- **整理动作 = 归类即出箱**：指定主题/分组（拖拽或属性区设置均可）后自动移出对应入口；支持直接删除；**不做 Note→Memo 转换**（Memo→Note 方向保留）。
- **剪藏即 Note**：每次剪藏生成一篇 Note 进收件箱，正文为网页正文的 Markdown 化结果；YAML 保存页面标题、来源 URL（`source_url`）、剪藏时间（`clipped_at`），页面能提供时另存作者（`author`）、发布时间（`published_at`）、站点名（`site_name`）、描述（`description`）、规范 URL（`canonical_url`），缺失项省略。
- 剪藏插件、Android App **属于后续规划**；当前先固定双入口的信息架构位置，不作为本轮核心实施前置条件。
- AI Agent 新建的 Memo 仍进入 Memo 时间线（Memo 无归属概念）；Agent 内容带来源标记，详见第十一章。
- **收藏网址**与**剪藏网页正文**是不同动作：收藏网址将 Raindrop 兼容的收藏记录追加到用户指定的记录 Note 或多维表格；表格是后续推送到 Raindrop 的优先来源。网页正文剪藏另生成 Note 并进入收件箱待整理。两者共用浏览器扩展与授权 Token，但数据写入目标和动作不同；详见第七章。
- **剪藏模板库**：适配规则以 Menote 自有、版本化声明式数据保存；支持 JSON 导入、手工/网页点选制作、项目设置管理及扩展周期同步。扩展制作器在独立页面打开当前网页的静态副本，支持选择字段、点选删除无关元素、查看可取得的 Raindrop 类页面属性、编辑并预览 Markdown；用户可保存可复用模板或直接剪藏最终正文。模板仅描述 URL 匹配、CSS 选择器、字段和排除项，不执行任意脚本；模板缺失或执行失败时回落通用剪藏。模板读写权限与笔记内容读取分离。

### 2.3 侧边栏与视图

左侧导航顺序：

1. **Memo 快速输入框**。
2. **新建笔记**按钮。
3. 回看入口：**Memo 时间线 / 最近编辑 / 收藏**。
4. 待整理入口：**收件箱 / 草稿箱**（见 2.2）。
5. **主题与分组树**（含固定的「私人空间」加密主题），以及**标签**入口。

搜索入口位置待定，确定前不放回侧栏；`design.html` 是视觉参考。

创建交互：

- **Memo**：默认单行输入；点击展开为多行，**占用“新建笔记”按钮所在的共享区域**，其余导航不被向下推，也不向右弹浮窗。保存后恢复原布局并留在当前页面；未完成草稿在收起时应保留。
- **Note**：点击“新建笔记”立即打开空白文档编辑页，**先写再分类**，不弹出必填归属表单。
- 两种创建态互斥，不需要同时展开。

正式笔记提供两种布局：

| 布局 | 结构 | 交互 |
| --- | --- | --- |
| **列表** | 左侧主题树 / 中间笔记列表 / 右侧文档 | 选中主题或分组后，中栏按下方显示规则列出对应笔记 |
| **网格** | 左侧主题树 / 右侧笔记卡片网格 | 打开卡片进入独立文档阅读/编辑区域，并能返回网格 |

**目录与清单显示规则（v0.7 补充设定）**：

- **左侧目录树只显示层级单位**：主题与分组，**不显示笔记**。
- **中间清单聚合展示（穿透）**：选中某层级后，中间清单显示该层级下的**全部笔记**——直属笔记与子层级（分组）内笔记递归聚合、扁平排列；选中分组时显示该分组内笔记（分组下无子层级）。
- 该规则同时适用于列表与网格两种布局；收件箱/草稿箱为独立固定入口（见 2.2），不在此层级规则内；「私人空间」主题遵循同一显示规则，锁定态约束见第五章。清单的具体呈现形式（是否显示分组标识等）暂不约束，留待界面设计。

**正式笔记上下文菜单（v0.20）**：

- 主题与分组支持右键菜单：重命名、删除；主题另支持新建分组。删除沿用软删规则，不级联删除笔记。
- 笔记清单项支持右键菜单：移动到主题/可选分组、加入或取消收藏、移入回收站；操作复用既有内容服务。
- 支持鼠标右键及键盘上下文菜单键（或 Shift+F10）打开；Esc 与点击菜单外关闭。菜单须有清晰焦点态与可访问名称。

整体保留 Menote 简约、克制的视觉方向；不因架构整理而推翻全部既有设计语言。

## 三、Note：编辑器、属性与表格

### 3.1 编辑模式

- **默认：所见即所得编辑**，参考 Typora。标题、列表、引用、图片及表格呈现接近最终样式；在需要编辑具体语法的位置按需暴露 Markdown 标记。
- **仅保留两个常驻模式**：**编辑**与**预览**。预览模式以阅读为主，正文只读。
- 不保留“纯源码编辑”“即时渲染”“分屏”作为并列的日常模式。
- 必要的 **Markdown 源码查看/编辑**可作为“更多操作”中的高级入口，具体入口及行为尚待细化，不构成第三种常驻模式。
- **内容解耦（v0.7 总原则）**：编辑器内部模型（AST）仅存在于编辑会话，**持久层只保存 Markdown 源文本**；不支持的语法原样存储、降级显示，绝不剥离或静默改写。详见「最终原则」。
- **选中浮条（v0.7 补充）**：编辑模式下选中字符可弹出快捷样式工具条，提供常见快捷样式（加粗、斜体、删除线、行内代码、链接等）；具体样式集与交互细节属 UI 设计。Memo 的源文本编辑同样可用浮条插入 Markdown 标记，与「无常驻格式工具栏」约定不冲突（见 4.1）。

### 3.2 YAML：独立的内联属性区

文档内部自上而下为：**标题 → 属性区 → Markdown 正文**。

- YAML Frontmatter 保留在 `.md` 文档中，但默认**不显示为源码块**。
- 属性区使用与正文有明确视觉分离的轻量布局，默认显示为经过排版的属性值，**不是满屏输入框**。
- **点击值直接编辑**：文本直接输入、日期弹出日期选择、单选/多选直接选择、布尔值直接切换等。
- 属性区可折叠；空文档不铺设大量空字段。
- **即使正文处于预览模式，属性区仍允许独立编辑**；写回需经统一文档更新链路，避免与正文自动保存冲突。
- 支持自定义属性类型、外来 YAML 键与未知值原样保留；属性的**显示名只影响 Menote UI，不改变 Markdown 中的原始键名**。
- YAML 解析与写回应保持往返兼容；不因为类型控件无法识别值就擅自清空、覆盖或丢弃数据。
- **类型集合（v0.7 定稿）**：v1 支持 8 种——文本、多行文本、数字、日期、单选、多选、复选框、链接（URL）；与表格字段控件共用同一套定义与序列化规则（表格侧因单元格禁换行不提供多行文本）；日期时间等类型为后续扩展。
- **定义存放**：类型/显示名定义存在该 Note 自己 YAML 的保留命名空间（键名技术设计时定）；单选/多选候选必须显式定义；主题级/全局 schema 继承列为后续增强。
- **无定义键**：按值做安全推断——能无损解析为日期/数字/URL/布尔才启用对应控件，否则一律文本；解析失败或编辑冲突一律文本降级、原样写回。
- **外来值兼容细则**：无法按声明类型解析的值降级为文本显示与编辑，保存原样写回，不报错阻断、不自动转换、不丢弃。属性区多选在 YAML 中是原生数组，不受表格单元格逗号契约约束。

### 3.3 Markdown 表格

**表格始终以标准 Markdown 表格为内容载体，结构化能力只增强编辑体验。**

- 编辑时提供类似飞书多维表格的**单元格编辑与字段类型控件**；预览时显示普通 Markdown 表格。
- 计划支持常用字段类型：文本、数字、日期、单选、多选、布尔/复选框、链接等；字段类型定义可利用 YAML 元数据，尽量复用 Note 属性编辑器的控件与规则。
- 没有字段定义的普通 Markdown 表格仍应可编辑；类型定义是增强信息，**不是打开表格的前提**。
- 明确**不做复杂公式、自动化、跨表关系或数据库式工作流**。目标是简单好用的记录清单。
- 自定义字段的序列化必须保持普通 Markdown 阅读器可读；多选分隔、特殊字符和换行的写回契约**仍需单独确认**。
- **文档身份（v0.7 定稿，双轨）**：Note 内任何 Markdown 表格均可进入结构化编辑（增强是编辑器能力，跟随内容）；「以表格为主体、YAML 携带字段定义」的 Note 作为第三方表格连接器（如 Raindrop）的**绑定目标**——它是 Note 的一种用法，不是第三种内容形态。浏览器收藏可以追加到记录 Note 或该表格；以 Markdown/YAML 作为可移植内容载体的原则不变。
- **字段配置**：持久字段定义只存在于表格主体文档的 YAML（如 `fields:` 结构，键名技术设计时定）；Note 内表格一律无类型编辑，可手动「抽出」为独立表格文档。
- **类型推断**：v1 不做自动类型识别；无定义表格的单元格一律按文本编辑、所见即写回。
- **多选写回契约**：`值A, 值B`（逗号+空格分隔）；配套硬约束——候选值禁止包含逗号（校验强制）、单元格内容禁止换行、竖线按 GFM 规则转义、值首尾空格不保留（GFM 会 trim）。
- **外部数据接入不改变此原则**：表格仍是通用 Markdown 表格，第三方连接器只负责数据读取、字段映射、写入和回传；不能把表格变成 Raindrop 专属内容类型。

## 四、Memo：时间线、todo 与图片浏览

### 4.1 基础交互

- **时间线是 Memo 默认视图**；Memo 轻量、原位编辑，支持必要的 Markdown 样式，不打开完整 Note 编辑器。
- 内容修改、标签与图片均依附于原 Memo 记录；Memo 不强制出现 YAML 属性区。
- **语法范围（v0.7 定稿，轻量集）**：块级——段落、有序/无序列表、任务列表、引用、fenced 代码块（无高亮或基础高亮）、分隔线；行内——加粗、斜体、删除线、行内代码、链接。不支持标题、表格、脚注；图片不走手写语法（附件上传自动插入引用）。**不支持 ≠ 改写**：超集语法原样存储、降级显示。
- **任务列表复选框**：正文 `- [ ]` 渲染为复选框且**可点击**，点击改写正文中的 `[ ]`/`[x]`；它是内容级清单，与侧边 todo 的结构化 `status` 相互独立、互不驱动。
- **编辑态形态**：源文本编辑（等宽纯文本，所见即源码）+ 保存/失焦后渲染显示；与 Note 的所见即所得编辑器彻底解耦。无常驻格式工具栏，手写 Markdown + 快捷键，后续可加极简工具栏；编辑中选中字符可弹出快捷样式浮条（见 3.1），与「无常驻」不冲突。
- Memo 的标签属于内容分类；**todo 状态是独立的结构化字段，不用 `#doing` 之类的标签承担状态语义**。

### 4.2 todo：Memo 内的侧边面板

todo **不再拥有独立完整页面**，仅在 **Memo** 视图旁作为可展开/折叠、且不遮挡时间线的辅助面板出现；不延伸到正式 Note 阅读区。

todo 只有**一个互斥状态字段**，分为三个组：

| 分组 | 状态值 | 行为 |
| --- | --- | --- |
| 待办 | `todo` | 新任务的默认位置 |
| 进行中 | `doing` | 将任务拖入此组即更新状态，可拖回“待办” |
| 已完成 | `done` | 在任何未完成组勾选任务，即自动进入已完成 |

固定交互：

- **拖拽到其他分组** = 修改状态；不增加“进行中开关”等第二维度。
- **勾选** = 完成并移到“已完成”；取消完成 = 回到“待办”。
- 三个标题只是面板里的**界面分组**，**不写入 Memo 正文**。
- 不再使用三段流程的强制推进按钮，也不需要另设状态下拉框。
- 普通 Memo 没有任务状态；转为 todo 时设置 `todo`；移除 todo 属性后恢复普通 Memo。
- 已完成分组可默认折叠，节省面板空间。

### 4.3 图片瀑布流（非当前必做）

- 基于**同一批 Memo 数据及其图片附件**，增加图片筛选/瀑布流浏览；**不是独立图库内容类型**。
- 每张图片可独立成卡片，一条 Memo 的多张图片均可出现；点击图片查看大图，并可定位到来源 Memo。
- 复用日期、标签筛选；优先缩略图与懒加载，注意大量图片的滚动和内存性能。
- **明确延期**：作为后续体验扩展，不阻断当前核心架构的完成。

## 五、加密：固定私人主题与单篇密码保护（核心功能）

### 5.1 两种作用域，不增加第三种

| 能力 | 固定加密主题「私人空间」 | 普通主题内的单篇加密 |
| --- | --- | --- |
| 主要用途 | 生活记录等不希望他人查看的私人资料 | 工作或其他普通主题中个别需要保护的内容 |
| 归属 | 系统固定的唯一加密主题，可包含分组和多篇 Note | **留在原主题/分组**，不因加密而搬走 |
| 解锁方式 | 主题级「锁定 / 解锁」；解锁一次可访问本区全部内容 | **打开该篇时输入密码**；仅解锁当前笔记 |
| 锁定范围 | 统一锁定该加密主题的内容 | 仅锁定选中的笔记，不影响其他内容 |
| 界面状态 | 主题上明确的锁定/解锁状态和手动锁定入口 | 单篇笔记有锁标识与密码输入界面 |
| 是否为当前核心 | **是** | **是** |

**确定不做**：允许任意普通主题一键整体加密；也不因单篇加密而创建其他特殊内容类型。Memo 不进入固定私人主题；本轮加密设计对象为正式 Note。

### 5.2 交互与状态

- **私人空间**：锁定时不能读取其中的正文和附件；解锁后，该主题里的笔记按普通 Note 的方式浏览与编辑；用户可以随时执行「锁定」。建议新会话默认锁定，具体超时锁定策略待技术设计。
- **单篇加密**：普通主题中的受保护笔记保留原位置；点开后显示密码输入，验证成功后才展示正文并允许正常编辑。默认离开该笔记后重新锁定（具体如何处理编辑中的未保存改动需在实现时保证安全）。
- 两种解锁**作用域相互隔离**：解锁私人空间不能解锁工作主题的单篇加密笔记；解锁单篇也不能解锁私人空间。
- **解锁不等于分享**：向同事展示或分享某一篇内容，不得顺带暴露其他笔记或整个私人主题。分享链接/授权机制应独立设计，不因本机解锁而自动放宽服务端访问控制；是否支持加密笔记的直接在线共享待后续确定。

### 5.3 数据安全的最低要求

- “密码保护”必须是**真实的内容加密**，不能仅靠 UI 隐藏或一个前端密码框。未经授权不能通过接口直接获取正文、附件明文。
- 加密正文及相关附件；缩略图、索引、检索摘要、缓存、历史版本和备份是否泄漏敏感内容，需要按同一安全边界处理。普通主题的单篇加密至少不能泄露其正文内容；标题等元数据的可见范围需明确约定。
- 可复用底层加解密组件，但**主题密钥作用域**和**单篇密码的授权作用域**不能混为一体；不以“加密整个主题成为一个大文件”为目标，避免影响单篇修改和同步。
- 必须明确密码修改、遗失/恢复（若无恢复能力需明确提示）、离线访问、换设备解锁与备份恢复的行为，具体密码派生、密钥包装、加密算法和数据迁移由技术方案确定。
- **三套凭据分离（v0.7 定稿）**：登录密码 ≠ 私人空间密码 ≠ 单篇笔记密码，互不连坐；拿到登录态 ≠ 能看私人空间。实施前勘查 V1 隐私锁/单篇门禁的密码体系是否已如此分离。
- **锁定策略**：新会话默认锁定 + 不活动超时自动锁定（默认 15 分钟、可配置）+ 随时手动锁。
- **标题明文（v0.7 定稿）**：加密笔记的标题保持明文——锁定时列表可辨识（否则无法知晓加密内容）、可按标题检索；**正文与附件始终密文**，锁定态不可访问；缩略图、历史版本、缓存仍只处理密文。已知并接受的边界：服务端存储与列表接口中标题为明文元数据。**MCP 边界 `[第五批修订]`**：单篇加密 Note 标题可查、接口反馈加密状态、内容不可读不可写；私人空间对 MCP 完全不可见（含标题，见 11.1）。
- **密码恢复机制 `[第五批后定稿]`**：采用**单一恢复码体系**——全账户一个高熵恢复码；任何启用加密的内容密钥（私人空间密钥、单篇内容密钥）在密码包装之外**同时用恢复码派生的 KEK 包装**（新增 `k_wrapped_recovery`，明文码永不入库）；遗失密码时凭恢复码解锁/重设，换码时统一重包装所有受覆盖的密钥；解锁状态下可查看引导与轮换。**后台密钥重置 / 服务端托管解密 `[第十一批修订]`**：不作为当前机制（当前恢复路径 = 恢复码）；列为**可能新增的后续能力方向**——若引入属安全模型重大变更（服务端将持有解密能力），必须专项安全审查并修订安全不变式后方可实施。**恢复码遗失 = 对应内容永久不可解**，设置与备份流程须强提示；**风险注记**：单码泄漏的爆炸半径为全部加密内容，UI 须明示。备份信封同步携带恢复码包装块（整理稿见 `archive/Menote_V2_平台能力功能设计_v0.2.md`）。
- **信封加密方向（v0.7 定稿）**：每篇 Note 独立内容密钥；私人空间内笔记的密钥由主题密钥包装（解锁一次全开）；单篇密码独立派生包装该篇密钥；算法选型（AES-GCM + Argon2id/PBKDF2 等）留技术设计。

## 六、数据存储、同步与导出

### 6.1 记录粒度 ≠ 物理文件粒度

**不采用“一条 Memo 对应一个物理文件”的运行时模型。**

- **Memo**：数据库中每条 Memo 有独立 ID 和记录；正文为 **Markdown 字符串**，创建时间、修改时间、标签、todo 状态等采用结构化字段。按记录插入、更新、查询，不需要为了修改一条 Memo 重写整个月份的 JSON 文件。
- **Note**：Markdown（含 YAML）是规范文档内容；数据库可管理文档索引、归属、版本与同步，但不改变 Markdown 的可移植性。
- 可沿用或重组现有 **IndexedDB（本地）+ Cloudflare D1（云端）** 的持久化与同步能力；具体表结构与事务、冲突策略属于技术设计。
- **JSON 是结构化数据表达方式，不等于必须将每个月的数据实时存成一个 `.json` 文件**。

Memo 逻辑记录示例（仅示意数据模型，不是最终数据库表结构）：

```json
{
  "id": "memo_001",
  "content": "今天整理了 **Menote** 的交互方案。",
  "createdAt": "2026-10-31T08:00:00Z",
  "updatedAt": "2026-10-31T08:00:00Z",
  "tags": ["Menote", "设计"],
  "status": "doing"
}
```

普通 Memo 的 `status` 为 `null` 或不设置。`todo / doing / done` 只用于 Memo 的任务辅助视图，不与 Note 属性的同名字段混淆。

**Memo 存储口径（v0.7 明确）**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 全局唯一、生成后不变；同步与引用的锚点 |
| `content` | string | Markdown 正文，**唯一内容真相** |
| `tags` | string[] | 内容分类标签；任务状态不用标签表达 |
| `status` | `todo` / `doing` / `done` / `null` | 任务状态；`null` 为普通 Memo |
| `attachments` | 附件引用[] | 指向附件存储的引用 ID；正文内以引用语法插入 |
| `source` | string | 来源标记：手动 / Agent / 采集（配合 11.1 落箱与审计） |
| `createdAt` / `updatedAt` | timestamp | 创建与最后修改时间 |
| `deletedAt` | timestamp / null | 回收站与同步墓碑标记 |

- **存储分工**：本地 IndexedDB 保存运行时权威副本（离线可用、多标签页协调）；云端 D1 保存同步权威副本（多端同步基准）；附件本体存 R2，记录只存引用 ID。
- 同步以**单条记录**为增量单位（outbox 模式），运行时不采用按月文件分片存储（分片仅属于备份工件，见 6.2）。
- 上表为**字段口径定稿**，具体表结构、索引与迁移仍属技术设计；备份 JSON 需完整覆盖上述字段。

### 6.2 备份与导出

- **JSON**：优先作为完整恢复所需的结构化备份载体，保留记录 ID、时间、状态、关联和必要版本信息。
- **Markdown**：作为通用、可迁移的内容导出格式；Memo 导出时按约定生成 YAML + Markdown，Note 尽量保持原始 `.md` 内容。
- **按时间段组织 Memo 备份**（例如每月一个分片），而不是一条 Memo 输出一个备份文件；具体按月/按年、快照与增量策略待定。
- 定期备份需覆盖**历史记录在后续月份被编辑或删除**的情况，不能只备份“本月新增”。
- **图片/附件引用与管理 `[第七批定稿]`**：
  - **md 正文引用格式**：相对路径 + 内容寻址——`attachments/<sha256>--<原文件名>`，与备份包路径同构（导出 / 备份 / 恢复三链路一致）；应用内渲染时把相对引用解析为鉴权 URL。
  - 引用对齐与渲染分两层：同步与引用计数继续用正文引用的附件哈希列表（`attachmentRefs`），md 中的相对路径服务于渲染与导出。
  - **导出形态**：默认 zip（`.md` + `attachments/` 目录，仅含被引用附件），解压即可在 Typora / Obsidian 等工具完整阅读；可选纯 `.md` 文件（图片断链时应用提示）。
  - **加密附件**：解锁并导出时附件随行**明文**；未解锁不导出该篇或明确提示（与「导出加密笔记须先解锁」一致）。
- **远程备份是核心需求**：支持将完整可恢复的数据快照持续备份至 **S3 兼容存储**与 **WebDAV**，可配置目标、凭据、调度与手动执行；详见第十一章。
- **区分两条链路**：本地下载 JSON/Markdown 文件服务于导出与迁移；远端备份服务于持续灾难恢复，不能把“导出成功”替代“远端备份可恢复”。
- **快照模型（2026-11-01 修订）**：每次备份执行生成独立时间戳目录，内含当前完整状态的月度 JSON 分片、被引用附件、manifest 与 COMPLETE；目录默认位于目标远端 `menote/` 命名空间下。daily/weekly 调度只是执行频率，仍走同一完整快照流程；恢复 = 读取所选快照目录并通过 manifest/COMPLETE 校验重建，无重放链。
- **保留策略（2026-11-01 修订）**：每个目标可设快照数量上限，默认 0=不限；配置上限后，成功推送时只删除超额的最旧 Menote 快照目录。用户可查看和手动删除单个远端快照，需显著说明并确认；任何操作不触碰路径以外或非 Menote 命名内容，也不影响本地数据。
- **加密入备份（v0.7 定稿）**：加密笔记/附件以密文 + 密钥包装元数据写入备份；恢复需用户凭据，无凭据 = 不可恢复（UI 明确警示单篇密码遗失不可找回）；主密码/明文密钥绝不入备份。
- **同构导出（v0.7 定稿）**：手动导出与远端备份使用同一备份包格式（导出 = 手动触发一次备份包生成并下载）；备份包 = 结构化 JSON + 附件文件 + manifest（版本与哈希）。

## 七、外部数据源与浏览器收藏（后期扩展）

### 7.1 定位与范围

- **已确定方向，非当前必做**：不重新开发 DogEar 式的独立书签系统；利用 Menote 的**通用 Markdown 表格编辑能力**管理外部结构化记录。
- **连接器是数据中间件**：接入第三方 API，映射到指定表格的字段，支持用户手动**下载 / 上传**，而不是定制一套 Raindrop 专属表格或管理界面。
- **首个验证对象为 Raindrop**：当前已有约 **414 条书签**，希望改善浏览体验、在表格内编辑，并建立独立备份。数量是本轮评估时的现状，不是产品限制。
- 先验证单个适配器，再决定是否抽象为通用插件 SDK；本轮**不要求提前建设完整插件生态**。

### 7.2 三层职责与两种写入入口

```text
浏览器扩展（未来）                  Raindrop 连接器（未来）
  ├─ 收藏网址 → 指定记录 Note/表格     ├─ 读取 Raindrop 收藏夹 / 书签
  └─ 剪藏网页 → 新建 Note → 收件箱      ├─ 字段映射 / 外部 ID 关联
          │                            └─ 比对 / 上传 / 下载
          ▼                                   │
  一篇 Markdown 记录 Note                     ▼
   追加并集中保存 URL                 Menote 通用 Markdown 表格
                                             阅读 / 字段编辑
                                                  │
                                           手动确认同步
                                                  ▼
                                             Raindrop
```

- **浏览器扩展**是通用内容录入入口：用户选择“收藏网址”时，提取 Raindrop 兼容字段并追加到指定 Note 或多维表格；收藏不创建收件箱 Note。用户选择“剪藏网页”时保存网页正文并进入收件箱。
- 记录 Note 的定位输入为文件链接或文件 ID。现有 `Item.id` 可作为文件 ID；Menote 应用的规范 Note/Table 文档路径为 `/notes/<Item.id>`，解析路径末段得到 `Item.id`。追加格式与目标不存在时的行为由 TP3 技术设计确定。
- **剪藏网页**是另一种录入动作：保存实际网页内容，进入**收件箱**供后续整理；用户可以在需要时选择只收藏地址，或分别执行收藏与剪藏。
- 首版剪藏整个页面，不提供选区剪藏；若未来增加选区剪藏，默认将选中内容保存为 Memo。
- **Raindrop 连接器**是外部系统同步适配器：绑定某张表与指定账号/收藏范围后，负责**拉取远端、字段映射、差异比对和回写远端**，不直接定义新的笔记内容类型。
- **Raindrop 表格可接收浏览器收藏**：扩展收藏到表格的行可作为后续推送至 Raindrop 的数据；Note 目标仍作为可读的兼容写入方式，不承诺直接参与表格同步。
- **表格不依赖连接器存续**：断开 Raindrop 后，本地表格及内容仍可保留、阅读与编辑；连接器不应成为唯一访问这些书签的方式。

### 7.3 绑定与数据匹配

- 每一行拥有**稳定的 Menote 本地行 ID**；已关联远端的行另维护 **Raindrop 记录 ID**。二者不能互相替代；仅凭 URL 不足以保证可靠匹配。
- 建议将外部账户/收藏范围、字段映射、远端 ID、上次同步版本/时间、变更状态等**连接器技术元数据放在数据库中**，通过表格与行 ID 建立关联；不要求把这些内部状态逐列写入可移植的 Markdown 表格。
- 表格中的通用列可映射标题、网址、标签、描述、收藏夹等；某些第三方字段不可编辑或无法回写时应明确标识，不能虚假承诺全字段双向修改。
- 两种入口对已有网址可能产生重复记录：优先依据远端 ID 匹配已同步行；遇到相同 URL 时可提示用户确认合并，**不自动将“同网址”当成同一书签**。

### 7.4 最小双向同步流程

1. **绑定**：用户指定一张表，选择 Raindrop 账号与同步范围，确认字段映射。
2. **下载**：分页拉取远程书签；有已知远端 ID 的更新已绑定行，未知的新增行；先检查本地未上传改动。
3. **本地编辑**：Menote 表格可编辑标题、链接、标签、描述等通用字段；浏览器扩展可将新收藏写入指定表格，并保留 Note 记录作为另一种目标。
4. **预览差异**：展示将新建、将更新、需人工处理冲突的记录；本地和远端同时更改同一字段时，不静默覆盖。
5. **确认上传**：未绑定远端 ID 的新行调用创建操作；已绑定且确有变更的行调用更新操作；成功后保存返回的远端 ID 与同步基线。

**边界规则**：首版采用**手动上传/下载**，不做实时自动双向同步；本地删除表格行**默认不触发远端删除**，如未来提供远端删除必须另行确认；防止双端反复覆盖、意外重复创建或将本地错误传播至云端。

**v0.7 补充定稿**：连接器实现为**服务端内置适配器**先行（仅 Raindrop），不做用户可装插件，是否抽象插件 SDK 待单适配器验证后再定；Raindrop OAuth 令牌与备份凭据同标准加密存储、设置页不回显；远端 ID、同步基线、字段映射、绑定状态等元数据存 D1，不写入可移植 Markdown；首版不提供远端删除入口；浏览器扩展为独立后续项目，不阻断连接器。

### 7.5 备份与规模

- Raindrop 同步**不等于备份**。需要独立的书签数据快照：优先 JSON 保留原始 ID、时间、收藏夹、标签及必要的源字段；Markdown/HTML 等作为可读、可迁移的导出选项。
- 同步后的表格也应能在脱离 Raindrop 的情况下浏览；但**一份可能被持续改写的表格不是历史版本备份的替代品**。
- 以当前约 414 条书签为起点，可先验证单表方案；若未来数据量显著增长，再评估表格大小、全文写回、增量同步与按收藏夹拆表，**不提前扩大核心表格系统的复杂度**。

### 7.6 分阶段安排（不阻断核心开发）

1. **只读验证**：连接 Raindrop、下载到指定表格、检查字段映射及浏览体验、生成独立备份。
2. **可编辑同步**：加入手动上传/下载、远端 ID 对应、差异预览与冲突保护。
3. **浏览器采集**：提供“收藏网址 → 追加到指定 Note/表格”与“剪藏正文 → 新建 Note 进入收件箱”两个并列入口；两种动作使用同一个 MCP Token，但写入目标独立。收藏字段兼容 Raindrop；从表格推送的采集时间映射到 Raindrop `created`。

> 已确认的是上述产品机制与职责边界；插件实现载体（内置适配器、独立插件、扩展 API）、授权方式、同步元数据表结构与具体交互样式，仍属于后续技术设计。

## 八、阶段划分

### 当前优先：核心闭环

1. 明确并稳定 **Memo / Note 双内容形态**及信息架构。

- **通用表格的外部数据连接器**：以 Raindrop 为首个验证对象，完成手动下载/上传与独立备份；浏览器扩展的网址收藏可追加至指定记录 Note 或表格，并保持剪藏正文进入收件箱的独立动作。详见第七章。
- 更复杂的内容组织、扩展能力与高级交互；不预先引入公式、自动化等非目标功能。

**最终原则**：**Memo 是数据库中的轻量记录，Note 是以 Markdown 为规范格式的正式文档；两者共享必要的 Markdown 表达能力，但不强制共享存储模型或完整编辑界面。** 安全保护是 Note 的权限与加密能力：**一个固定私人加密主题 + 普通主题内的单篇密码加密**，不制造第三种内容形态。一切附加视图（todo、瀑布流）、收集入口（收件箱、草稿箱、剪藏、Android）都依附于两个核心内容形态。**外部数据连接器属于通用表格的可选扩展**：浏览器收藏可写入指定 Note/表格，Raindrop 中间件使用绑定表格拉取与回写；收藏字段兼容 Raindrop，不建立第二套书签内容系统。

**内容解耦（可移植性第一，v0.7 起）**：编辑体验可以富，内容必须“裸”——持久层的内容真相只有标准 Markdown + YAML，编辑器内部 AST 仅存在于编辑会话；任一篇内容**单篇导出**或**从存储直读**（D1 / 备份 JSON），脱离 Menote 后仍完整、可被任何 Markdown 工具无损解读（外部阅读器忽略未知 YAML 键是允许的，内容本体不得依赖 Menote 才能解读）；不支持的语法原样存储、降级显示，绝不剥离、转义或静默修正。锁定态只能取得密文属访问控制而非内容耦合，导出加密笔记须先解锁。**md 中图片/附件的引用与管理已定稿**（相对路径 + 内容寻址 + 导出随行附件目录，见 6.2），本原则不再有遗留的随行部分。

### 10.4 必须优先验证的技术风险

1. **Typora 式编辑器 Markdown 往返**：不能因可视化编辑损坏 YAML、GFM 表格、代码块、附件引用及不认识的 Markdown 内容。
2. **Memo 数据契约**：结构化字段为唯一权威来源，同步与导出口径一致；不出现双份互相覆盖的状态（无旧数据迁移负担，契约一次做对）。
3. **加密**：主题锁与单篇密码不共享解锁授权；验证密码错误、换设备、离线访问与备份恢复（恢复码全链路）。
4. **同步冲突和离线编辑**：并发保存、重复提交、删除恢复、跨设备冲突不能静默丢失记录。
5. **MCP 安全边界**：外部 Agent 的授权范围、只读/写入权限、重复提交与编辑冲突必须有服务端保障，不得读取私人主题或单篇加密笔记明文。
6. **远端备份恢复性**：不能只测试上传成功；应验证加密备份、附件一致性、密钥恢复与完整重建；失败重试生成新快照，恢复端忽略缺少 COMPLETE 的目录。
7. **范围控制**：不要把后期剪藏、Raindrop 连接器和 Android App 提前加入 V2 核心交付范围。

## 十一、V1 既有平台能力：MCP 与 S3/WebDAV 远程备份（v0.5 补充）

> **范围定性 `[已定]`**：以下两项不是新提出的实验功能，而是 **V1 已经开发、V2 必须保留的核心能力**。它们与第七章的 Raindrop / 浏览器插件不同：**MCP 是对外 AI Agent 读写接口；S3/WebDAV 是用户数据的持续备份渠道**，均须在 V2 迁移上线前完成可操作验证。下列技术细节以 V1 实现作参考，V2 最终接口可随数据契约调整。本章及第十章所列全部 V1 复用能力（认证、同步、附件、版本/回收站、MCP、备份）的**功能级设计整理稿**见 `archive/Menote_V2_平台能力功能设计_v0.2.md`（按产品负责人指示暂归档，不作为现行规格）；下文 V1 参考实现链接仅作代码勘查参考，不作为设计依据。

### 11.1 MCP：让其他 AI Agent 安全访问 Menote

- **外部调用方**：Cursor、Claude Code、Codex 及其他支持 MCP 的 Agent，通过网络连接 Menote，不要求打开 Menote 网页，也不属于 Raindrop 插件的一部分。
- **至少保留的能力**：完整 MCP 保留查找/列出/读取/版本等 5 个读工具和创建/追加/编辑/表格行/归属/回收站等 6 个写工具，并新增受独立权限控制的附件上传、读取/下载能力。TP3 提前交付 Token 管理和剪藏所需的最小 MCP 写入/附件能力；其他 Agent 工具仍按 M4 计划完成。
- **Token 与权限**：Token 可创建、查看/复制、撤销；内容读取、创建、编辑、回收站、附件权限逐 Token 配置，内容读取可关闭；范围、Memo、URL 携带、有效期、限速等按 Token 维护。权限动态调整后立即影响下一请求，不重新签发 Token。记录每个 Token 最后一次认证成功的调用时间；无效 Token 不刷新时间。
- **Token 命名**：每个 Token 支持独立名称并可修改；新建时名称留空，按 `menote1`、`menote2` 等序号自动命名。
- **管理入口**：上述 Token 管理界面置于应用设置菜单的独立「MCP 接入」栏目，与远程备份、附件和恢复码设置并列。
- **连接信息可恢复**：管理页提供稳定 MCP 地址的复制操作及 Token 显式复显/复制；地址由当前实例 origin 加固定 `/api/mcp` 路径构成，不绑定到某个 Token。
- **必要协议读取**：关闭内容读取只屏蔽搜索、条目列举、正文、版本等既有内容访问；MCP 协议初始化/工具发现、身份认证、权限范围解析等服务运行必需的内部读取仍可执行，但不得借此向调用方披露既有内容。
- **加密边界**：私人空间（固定加密主题）对 MCP 完全不可见——不出现在目录树、列表与搜索中，条目数不含其中内容，无论用户是否在浏览器中解锁。单篇加密 Note 仅可按既有设计返回标题元数据与「已加密」状态；MCP 永远不得创建到加密空间、读取或编辑加密内容及其附件，附件权限不可覆盖此拒绝规则。
- **附件权限**：上传/附加需 Token 的附件权限与对应条目的创建/编辑权限；读取/下载既有附件还需内容读取权限与条目可见性。服务端按用户、Token 范围和条目状态逐次授权；不提供独立附件永久删除。
- **写入正确性**：Agent/剪藏新增与编辑必须走与 UI 相同的业务命令与数据验证路径；采用版本前置条件/冲突检测和重复操作去重，避免覆盖用户的新改动；变更进入正常同步、历史和审计流程；每次调用读取 Token 当前权限。
- **边界不扩大**：MCP 不是无权限的通用远程控制通道；备份配置、令牌机密、分享管理、加密密钥、内容永久删除和附件永久删除不作为可调用工具。
- **V2 适配重点**：主题/分组替换旧文件夹层级、todo 变为 Memo 结构化 `status`、表格继续以 Markdown 为规范格式；这些变动可能影响工具参数、检索结果、权限范围与版本号。应提供兼容迁移策略，不直接声称 V1 的 11 个工具无需修改即可运行。
- **工具契约适配（v0.7 定稿）**：V1 的 5 读 + 6 写按 V2 数据契约映射；工具名与参数**向后兼容优先**，无法兼容的工具提供版本标记与迁移指引。
- **MCP 新建落箱**：Agent 新建 Note → 收件箱待确认；新建 Memo → 时间线；MCP 新建内容带来源标记，至少区分 Agent 与浏览器剪藏 `clipper`，审计可查。
- **审计**：写操作与附件上传/读取/下载记录令牌 ID、工具、目标对象或资源、版本（适用时）、时间与结果，随操作日志存 D1；另在 Token 管理中展示最后调用时间；保留期技术设计定。
- **迁移兼容（v0.7 定稿）**：V2 上线**不自动迁移**旧 MCP 令牌与旧备份目标凭据，提供清晰的重新生成/配置指引（与 11.4 迁移验收项一致）。

V1 参考实现：[MCP 工具注册表](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/services/mcp/registry.ts)、[令牌契约](https://github.com/maxxie6418/Menote/blob/main/packages/shared/src/mcp.ts)、[可见范围过滤](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/services/mcp/scope.ts)。

### 11.2 远程备份：S3 / WebDAV 是核心灾难恢复能力

- **备份目标（2026-11-01 修订）**：每条备份路径独立添加，可选 **WebDAV** 或 **S3 兼容对象存储**；分别配置连接参数、名称、凭据、远端目录（默认 `menote/`）、手动按次或 daily/weekly 定时推送、保留快照数量上限（默认 0=不限）。添加前提供测试连接，验证目录访问与读写。
- **执行方式**：提供手动「推送一次」及可配置的定时推送。V1 已支持 `daily / weekly` 档位；V2 应优先继承这一简单口径，不先引入复杂调度平台。
- **数据内容**：远端备份覆盖 Note、Memo 结构化字段、主题/分组关系、附件及必要恢复元数据。每次推送生成独立时间戳快照目录，避免历史快照被覆盖；目录下包含按月 JSON 分片、附件、manifest 与 COMPLETE 校验标记。
- **安全**：备份凭据加密保存；**凭据回显原则 `[第十一批修订]`**——应用内配置的凭据（备份目标、MCP 令牌、监控 Token 等）默认不在界面明文展示，但**必须支持事后查看与复制分发**，为此采用可逆加密存储（替代仅哈希的不可回显方案）；出站备份和附件涉及的加密数据应维持必要的机密性与可恢复性。不得将用户主密码或明文密钥直接写进远端备份。
- **远端删除与管理（2026-11-01 修订）**：用户可展开目标浏览其配置目录下的 Menote 快照并删除指定快照；超过目标保留数量时自动清理最旧 Menote 快照。删除前需显著说明并确认，严格限制在目标目录内由 Menote 命名的快照，不影响本地数据或目录中的其他文件。
- **运行状态**：每个目标显示最后推送时间、最近成功/失败状态及可理解的失败原因；连接测试验证远端可读写。失败重试生成一份新的完整快照，不将残缺目录视作有效备份。
- **恢复**：必须定义并验证“从远端取回备份 → 校验清单与内容 → 取得必要解密凭据 → 在干净环境恢复”的完整演练。**V1 具备远端推送不等于 V2 已具备完整远端恢复 UI**；恢复路径需单独检查与补齐。

V1 参考实现：[备份目标数据契约](https://github.com/maxxie6418/Menote/blob/main/packages/shared/src/backup-targets.ts)、[远端备份推送状态机](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/jobs/push.ts)、[WebDAV 适配器](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/adapters/webdav.ts)、[S3 适配器](https://github.com/maxxie6418/Menote/blob/main/apps/worker/src/adapters/s3.ts)。

### 11.3 与 V2 其他模块的关系

| 模块 | MCP Agent 接入 | S3/WebDAV 备份 |
| --- | --- | --- |
| Note / Memo | 受限读写，遵守新数据契约与同步版本 | 保留完整记录和恢复所需元数据 |
| 通用 Markdown 表格 | Agent 可更新指定行，走统一表格写入命令 | 保存标准 Markdown 与必要字段定义 |
| 主题 / 分组 | 令牌仅可访问授权组织范围 | 恢复组织结构，不因迁移丢失归属 |
| 私人空间（加密主题） | 完全不可见、不可读取、不可修改 | 保留密文、密钥包装及恢复所需信息，不输出明文 |
| 单篇加密 Note `[第五批修订]` | 标题可查、接口反馈加密状态；MCP 不得创建到、读取或编辑，附件工具同样拒绝 | 同上：正文密文保存，不输出明文 |
| Attachment | 上传与读取/下载受独立 Token 附件权限、对应内容权限和条目范围共同控制；加密内容不适用，不提供独立永久删除 | 附件随条目及备份边界处理 |
| 搜索 / 历史 / 回收站 | 权限过滤、操作审计、避免重复写入 | 遵循备份范围与保留策略，恢复后可验证 |
| Raindrop 连接器 `[后期]` | 独立能力，不依赖 MCP 工具命名 | 第三方缓存与绑定元数据是否备份需后续明确 |

### 11.4 V2 验收底线

1. 内容读取权限开启的 Token 可查询/读取授权范围内的非加密内容；关闭时搜索、内容列举、正文和版本读取均拒绝，MCP 协议发现与鉴权仍可正常工作。创建/编辑等写权限按 Token 独立拒绝或允许。
2. 对已撤销/过期/越权令牌，服务端拒绝访问；权限动态修改下一请求生效；最后调用时间只由认证成功的 MCP 请求更新。
3. **私人空间完全不可见**；**单篇加密 Note 不得由 MCP 创建、读取或编辑，附件工具也不得添加或读取其附件**，无论浏览器解锁状态或 Token 附件权限如何。
4. 获得附件权限且具备对应内容权限的 Token 可上传并读取/下载授权明文条目的附件；缺少任一权限或越权访问均拒绝；没有附件永久删除工具。附件操作留审计记录。
5. 两次重复写入不应制造多份记录；版本不一致时返回可处理的冲突而非静默覆盖。写类工具保留审计记录。
6. 在测试目标中分别完成 **WebDAV 与 S3** 的连接验证、手动上传、计划推送、网络失败续传、远端内容完整性检查；并在空白测试环境执行至少一次**从远端备份恢复**，覆盖 Memo、Note、附件、主题归属与加密内容。
7. V1 无存量数据与配置迁移负担 `[第十二批修正]`；若外部 Agent 客户端曾配置 V1 令牌，提供清晰的重新生成/配置指引即可。

## 十二、Cloudflare GitHub 一键部署与零附加配置（v0.6 新增）

### 12.1 产品级硬性要求 `[已定]`

> **Menote V2 必须支持从 GitHub 一键导入 Cloudflare 并完成部署。用户在首次部署期间，除在 Cloudflare 环境中设置一个密钥之外，不需要创建资源、修改配置文件、添加环境变量或手动接线。**

- **部署入口**：项目仓库提供 **Deploy to Cloudflare** 一键部署按钮；同时支持从 Cloudflare Dashboard 的 Workers & Pages 选择 GitHub 仓库导入。用户完成 Cloudflare/GitHub 账号授权并选择项目即可走默认流程，无须本地安装 Node、Wrangler 或执行终端命令。
- **唯一必填部署 Secret**：沿用 V1 的 `AUTH_PEPPER`，由用户在 Cloudflare Worker 的 Secret 管理中设置。它属于部署时的**唯一应用级人工配置项**，不提交到 GitHub，不作为公开 `vars`，不通过构建日志、页面或错误信息回显。后续单篇笔记密码、用户登录密码属于应用业务数据，不算额外的部署环境变量。
- **单 Secret 推算义务（v0.7 补充）**：设计期必须按功能清单**推算**部署期所需的全部密钥与凭据，能复用、派生或首启自动生成的不得新增部署 Secret；若推算发现单一 Secret 无法覆盖，**必须尽早提出**并说明缺口与理由，不得留到部署验收阶段才发现。单 Secret 的具体密钥方案仍需按功能清单验证；应用凭据以防范日常基础安全风险为目标，控制复杂度与成本。应明确数据库泄露时的保护边界、凭据复显的身份验证、密钥恢复与轮换；不承诺数据库与其内密钥同时泄露时仍能保密。此原则不改变内容加密、恢复码及现有安全红线。
- **自动资源**：由项目预置的 Wrangler 配置触发 Cloudflare 原生 D1 数据库、R2 对象桶的自动创建和 Worker 绑定；不能要求用户手动查 `database_id`、输入 `account_id`、建立 Bucket 或复制资源 ID。应用依赖的 Static Assets、Worker API、Cron Triggers 也必须随项目交付配置就绪。
- **自动初始化**：首次启动通过可重入（幂等）的 schema 初始化/迁移完成 D1 表、索引及必要默认数据；不要求用户登录 Cloudflare 手动执行 SQL。部署脚本/运行时应具备迁移版本记录、失败停止或受控重试机制，禁止误把新旧 schema 混用。**资源自动创建是 Cloudflare 的能力，数据库 schema 自动迁移必须由 Menote 自己负责实现。**
- **自动持续部署**：Workers Builds 绑定 GitHub 主分支，后续 push 自动构建并部署；构建参数、工作目录、依赖安装/锁文件、产物路径、运行时兼容、静态资源路由均在仓库中确定，不能依赖用户手调 Cloudflare 构建命令。
- **默认可访问**：使用 Cloudflare 分配的 `*.workers.dev` 地址即可进入首次创建账号/初始化引导。自定义域名、独立 MCP 域名或其他高级网络配置均为可选项，不得作为首发可用性的前置条件。
- **配置自检**：启动时检测 `AUTH_PEPPER`、D1、R2、schema 版本与关键绑定；缺少 Secret 时必须拒绝敏感功能的正常工作，以清晰、可操作的错误指引完成**唯一必需配置**，绝不能静默降级成无密钥的生产环境；缺资源/迁移失败不能显示“部署成功可用”。

### 12.2 用户最短部署路径（成功口径）

```text
GitHub 仓库 → Deploy to Cloudflare / Cloudflare 选择仓库 → 授权导入
    ↓  项目自动安装依赖、构建、创建 Worker + D1 + R2 并完成绑定
    ↓  项目自动初始化/迁移 D1，部署静态资源和 API，配置 Cron
Cloudflare 环境 → 只填写一个 Secret：AUTH_PEPPER
    ↓
打开 workers.dev → 注册/初始化 → 新建 Memo/Note、附件上传可用
    ↓
后续 GitHub 更新 → Workers Builds 自动部署与安全升级
```

- **不得出现的必需人工步骤**：手动建 D1、手动建 R2 桶、手动配置数据库 ID/桶名/Binding、执行迁移 SQL、补第二个部署密钥、修改 `wrangler.jsonc`、写 GitHub Actions Secret、配置域名/DNS、启用额外付费服务才能让应用核心功能运行（Cloudflare 平台固有的服务开通例外除外）。
- **外部备份功能不等于部署配置**：使用 S3/WebDAV 远端备份时，用户需要在 Menote **应用设置页面**填目标地址和该存储服务的访问凭据。这属于用户主动启用外部服务的业务设置，**不要求写 Cloudflare 环境变量，也不阻断 Menote 初次部署**。Raindrop 同理，属于后期连接器授权。

### 12.3 平台前置条件与容错（不能混淆为产品配置）

- 用户必须拥有 Cloudflare 账号并授权连接 GitHub；这是平台身份和操作授权，不是 Menote 的额外配置。
- **R2 账号级启用例外**：截至本设计核验日，Cloudflare 的 R2 入门文档仍要求账号具有 R2 subscription；没有启用 R2 的账号可能需要完成一次平台服务开通流程。项目应明确提示此限制并尽量在导入时检测，**不可承诺绕过平台结算/服务授权**，也不应让用户随后手动建桶或绑 Worker。
- **其他按需启用服务的同类例外（v0.7 补充）**：Images Transformations、Queues 等 Cloudflare 服务如存在账号级订阅或付费计划要求，按与 R2 相同的原则明确提示**平台前置限制**，不作为部署前置步骤，也不承诺绕过（详见 13.2 注记）。
- 如果 Cloudflare 账号权限、计划限制、R2 未启用或自动资源预配失败，应明确报错并指出所需的账号级操作，不能无限重试、创建多份同名资源，也不能把失败伪装成已完成部署。
- 生产、预览及迁移测试环境的数据库/桶必须隔离；不能因为 Preview 构建而写入或清理生产数据。重复部署应重用已有绑定，升级不可重新创建孤立的新 D1/R2。
- `AUTH_PEPPER` 的遗失/轮换涉及现有加密封装和认证的安全迁移。除非完成兼容的密钥轮换设计，**不得用重置 Secret 作为普通故障恢复手段**。

### 12.4 验收标准与优先级

**优先级：P1，首个正式 V2 发布前必过；首个可部署的开发预览阶段就要验证最小导入路径。**

1. 使用全新 Cloudflare 账号或隔离的测试账号，从 GitHub 仓库一键导入；不预先创建 D1/R2，不修改 Wrangler、构建命令及资源 ID，证明自动创建与绑定成功。
2. 仅设置 `AUTH_PEPPER` 一项应用级部署 Secret，即可完成首次账号初始化、Memo/Note 保存、附件写入/读取、浏览器刷新后的数据保持；未设 Secret 时必须安全拒绝并说明处理方式。
3. 数据库初装与升级迁移完全自动、幂等；重复部署不丢现有数据、不重复建资源；失败后有清晰的诊断与恢复路径。
4. 提交一次 GitHub 更新，证明 Workers Builds 自动部署且不覆盖唯一 Secret、D1/R2 绑定、备份计划或现有数据。
5. 定时触发机制、MCP 入口、S3/WebDAV *功能入口*可用；后两者实际访问外部服务时才由用户按功能授权/配置，不能强制成为部署前置步骤。
6. 若账号尚未开通 R2 或缺少资源创建权限，部署引导应明确说明**平台前置限制**并阻止错误的“已就绪”判断；不要求为此补充其他应用环境变量。

## 十三、Cloudflare 服务优化与 AI 能力（v0.7 第四批收录）

> **来源与状态**：2026-10-31 设计讨论确定的产品方向，**产品原则已定稿，技术实现由架构阶段评估**。与既有章节的关系：单 Secret 部署（第十二章）不受影响——Workers AI 为原生 binding 无需密钥，监控增强模式的只读 API Token 属应用内用户配置（同备份凭据先例），12.1 推算结论经复算不变。

### 13.1 总体原则 `[已定]`

- 优先使用现有 Workers、D1、R2 的原生能力，避免无必要地增加基础设施。
- 新增服务需要具有明确的体验收益，且默认不产生额外付费。
- 保持 GitHub 一键部署，应用部署时仍然只要求设置 `AUTH_PEPPER`。
- 能够自动创建和绑定的 Cloudflare 资源，应由项目自行完成配置。
- 非必要的第三方服务应采用可选模块，不影响笔记的基本使用。
- 不为了增加技术服务而增加服务；优先完成现有架构的性能与体验优化。

### 13.2 Cloudflare 服务引入规划 `[已定]`

| 服务 | 应用价值 | 规划 | 边界注记 |
| --- | --- | --- | --- |
| D1 FTS5 | Note、Memo 全文搜索 | 优先利用 | 正文索引只收非加密正文；加密笔记标题为明文并支持标题检索，具体是否使用 FTS 索引及权限过滤方式待架构评估。离线检索仍走本地 IndexedDB，FTS5 承担服务端/跨设备检索 |
| D1 Time Travel | 数据库误操作恢复 | 利用原生能力 | 定位为**灾难恢复补充手段**：整库覆盖式恢复、时间窗口有限、操作在 Cloudflare 侧，**不能替代 6.2 的应用级备份** |
| Workers AI | 笔记摘要、标签推荐 | 近期引入 | 原生 binding、无额外密钥；详见 13.3 |
| Workers Logs | 错误排查、同步和任务异常分析 | 近期引入 | 免费额度内使用 |
| Images Transformations | 图片缩略图、压缩和格式优化 | 体验优化阶段 | 可能存在账号级开通（类比 R2 例外，见 12.3），引入前需与 V1 自产缩略图 PoC 对比 |
| Cloudflare Queues | 异步处理、批量任务和失败重试 | 按实际需要引入 | **核验义务**：历史上需 Workers 付费计划；免费不可用时以 D1 队列表 + Cron 等价实现（V1 推送状态机已验证该模式可行） |
| Web Analytics | 页面访问及前端体验统计 | 可选 | 默认关闭 |
| Vectorize | AI 语义检索 | 远期考虑 | 不提前建设 |

### 13.3 Workers AI：首期功能范围 `[已定，实现待架构评估]`

首期只实现以下两个功能：

**1. 文章摘要**

- 对正式 Note 生成简洁摘要；保留原文，不自动重写正文。
- **保存机制 `[已定]`**：生成结果先作**会话内临时预览**（可丢弃的派生缓存，不入文档）；用户确认保存 = **写入该 Note 属性区**（进 YAML、进 `.md`、随导出携带），复用属性编辑器控件与统一文档更新链路；内容变化后允许重新生成，按内容版本（`rev`/`content_hash`）复用未过期结果。

**2. 标签推荐**

- 分析 Note 或 Memo 内容，推荐少量相关标签；优先从用户已有标签中选择，减少重复和近义标签。
- 用户确认后才写入标签；不自动修改主题、分组和笔记归属。

**AI 设计原则 `[已定]`**

- 使用 Cloudflare Workers AI 原生 Binding，不要求额外模型 API Key。
- 优先测试低成本中文模型；候选模型：**Qwen3-30B-A3B 与 GLM-4.7-Flash `[第五批修订：双候选待定]`**——先尝试走通其中一个即可（当期 Workers AI 目录可用性与 Neurons 定价以部署时核验为准），保留模型替换能力。
- 默认手动触发，不在每次编辑、保存时调用；控制输入和输出 Token，避免无意义的重复推理。
- 根据内容版本复用未过期的 AI 结果。
- 加密内容默认不提交云端 AI，必须由用户主动授权。
- AI 功能可以关闭；额度不足或服务不可用时不影响正常编辑。
- 首期仅实现上述两功能；对话、知识库问答、自动分类、自动执行等更多 AI 能力为**额度满足下的后续体验扩展方向**，逐项评估引入、不提前建设 `[第十一批修订]`。

**加密内容 × AI 的授权流程 `[待架构评估，安全性关键]`**

- 待定项：解密位置（客户端解密后送推理 / Worker 端解密）、授权粒度（单篇 / 每次 / 批量授权）、**AI 结果本身的存储边界**——摘要与标签是内容派生明文，授权加密内容生成的结果不得以明文落服务端（候选：仅本地会话内、或随条目加密存储）。
- 此项必须在 AI 功能验收（13.7）前定稿。

### 13.4 Cloudflare Resource Monitor：独立资源监控模块 `[产品原则已定，官方增强模式提前至 M2]`

**定位**：让用户及时了解 Cloudflare 资源消耗、距离免费额度的剩余空间及潜在费用风险。必须与 Menote 的笔记业务解耦，未来可复用于其他 Cloudflare Workers 应用。

**监控范围**：Workers（请求量 / 错误率 / CPU）、D1（读写行数 / 存储）、R2（存储容量 / Class A/B 操作）、Workers AI（Neurons 消耗 / 推理次数 / 估算成本）、Images（转换用量）、Queues（启用后）；未启用的服务不显示无意义数据。同时支持按应用查看和按 Cloudflare 账户查看——**账户共享额度不能错误地当成某个应用独占的免费额度**。

**两级监控机制**：

- **基础模式（零配置）`[已定]`**：Menote 内部记录自身关键操作与 AI 调用，统计次数与处理量，按已知免费额度做趋势估算；不需要额外环境密钥；**必须显著标注「仅本应用统计 + 估算值」，不声称等于 Cloudflare 官方计费量**，账户共享额度的局限须明示。
- **增强模式（官方数据）`[M2 可选]`**：通过 Cloudflare 官方 Analytics GraphQL API 查询；用户在系统状态页自愿配置 Account Analytics Read Token、Account ID 和项目资源标识（Worker 脚本名、D1 Database ID、R2 Bucket 名称）；Token 使用 `AUTH_PEPPER` 派生密钥在服务端加密保存，默认不显示，用户显式操作后可查看/复制；不返回到普通配置接口，不写日志。展示采集时间与可用性；没有填写资源标识或无对应指标时明确提示，不读取或冒充整个账户为本项目数据。**不作为 GitHub 一键部署的前置要求**。

**监控面板**：资源卡片按 Worker、D1、R2 分组，展示所选今日/本月周期的请求、错误、CPU 分位数、行读写、数据库大小、对象数与存储容量；提供手动刷新与 5/15/30/60 分钟刷新频率设置，显示最近更新时间；从用户名菜单进入后在应用右侧主内容区呈现，保留侧栏与主界面上下文；**明确区分官方统计、应用内部统计、估算数据三类口径**，不得混合成看似精确的账单数字。官方 Analytics 统计不等同账单且存在延迟；应用内部抽样估算仅代表本应用，不得称为官方计费量。

**额度预警与保护**：分级阈值 70% 提醒 / 85% 警告 / 95% 高风险（可调整）；对可主动控制的非核心功能提供本地预算保护——AI 接近预算暂停自动/批量推理、暂停非必要图片批量转换、后台任务限流避免连续重试；**配额不足时优先保证笔记阅读、编辑和数据安全**。

**预警不等于收费硬限制**：Cloudflare 统计存在延迟，付费计划可能在超过免费额度后继续计费；监控模块不承诺阻止全部账单，必须结合应用内部限额与用户自身的套餐设置控制风险。

**模块边界与复用**：独立的数据采集与归一化层、独立的免费额度/统计周期/阈值配置、独立的监控视图与状态组件；通过统一接口接收应用身份和监控配置；可逐步支持多个 Cloudflare 项目。首期先服务 Menote，**不要求当前即建设通用监控平台**，但模块边界应允许未来抽离为独立软件包。

### 13.5 成本与部署约束 `[已定]`

1. 首期 AI 默认以 Workers 免费额度为目标，不依赖付费模型。
2. AI 调用设置应用内部预算，不允许无限批量执行。
3. Resource Monitor 采用低频采样、查询缓存和适量历史存储；监控自身写 D1 亦消耗额度，计入采样频率设计。
4. 新增 Cloudflare Binding 尽可能通过项目配置和部署流程自动完成。
5. 官方账户 Analytics API 需要的额外只读授权属可选增强能力，不影响首次部署。
6. 免费额度与价格使用可更新的配置，不将当前数值永久写死在业务代码中。

### 13.6 与里程碑的对齐 `[已定，第十二批改版]`

- **M2 提前项**：Resource Monitor 官方 API 增强模式（用户自愿配置，FR-MON-4）；未配置时保留零配置应用抽样模式。
- **M4 扩展能力**：Workers AI 摘要与标签推荐、D1 FTS5、Workers Logs、样式后台编辑 UI（FR-STYLE-2/3）。
- **M1 挂载**：Resource Monitor 基础模式——**尽早完成、尽早接入、尽早监控**（第五批指示），不等待扩展里程碑整体排期。
- 扩展项不阻断 M1~M3 核心里程碑（范围控制原则，10.4-7）。

### 13.7 验收原则 `[已定]`

- AI 能够生成摘要和标签建议，且未经确认不修改原文与归属。
- AI 不可用时，基本笔记功能完全正常。
- 资源面板能够展示真实或明确标记为估算的消耗数据，三类口径不混淆。
- 额度接近阈值时能够有效提醒；本地限额可以限制应用主动发起的 AI 请求。
- 监控自身不造成明显的性能及费用负担。
- 不添加必填部署密钥，保持原有的一键部署体验（第十二章验收口径不变）。
- 资源监控代码与 Menote 业务模块解耦。
- **加密内容未经用户显式授权不进入云端 AI**；授权流程与结果存储边界在架构阶段定稿并通过验收。

**最终原则**：Cloudflare 的免费能力用于改善体验，Workers AI 只做轻量内容辅助；Resource Monitor 负责资源可见性、风险预警和应用级用量保护，并为其他项目复用保留架构空间。
