**数据干净准确的保障机制**（对应负责人「不要弄坏线上」）：行 ID 锚定 + D1 账本，绝不按位置或 URL 推断身份；baseline 快照防回声循环（拉取写入同时刷新基线，行内容已等于远端时只对齐账本）；冲突保护三态（本地未同步修改 × 远端变化 → `conflict` 不覆盖，等人工）；同 URL 不自动合并（照常追加并计入 skipped/新增可查）；远端消失、本地删行均只标记（`remote_missing`/`orphaned`）不删除，首版无远端删除入口；写表格一律走 `applyOperation`（rev 冲突整轮失败不落盘，下轮重试）；单次写入失败时账本不动（回声判定保证下轮可安全续推）；R2 快照内容 hash 复用 + 保留最近 100 份。

## 2026-11-03：阶段 B 手动反推（0.1.4）

**实现**：在阶段 A 账本上补手动推送，不改需求口径（仍是 v1.27 / 主文档 v0.24：预览确认后才写远端，推送永不删除远端收藏）。

- `raindropApi.ts`：`getRaindrop` / `createRaindrop` / `updateRaindrop`（PUT 只带差异键）、`findRaindropByLink`（精确链接全量扫描，不用搜索语义）、`diffFieldKeys`。`type` 不在可写键里（Raindrop 自行判定）。`capturedAt` 任一侧为空或不可解析时视为通配相等：不把空的「采集时间」推上去覆盖远端 `created`，也不让服务端补的时间戳把未填时间的行永远标脏。
- `raindropService.ts`：`planPush` / `previewPush` / `runPush`。未绑定行创建；已绑定且行内容哈希 ≠ 基线则更新；`remote_missing` 不重建；本地已删行不在表里，自然不推。更新前 GET 回读，远端相对基线有漂移则标 `conflict`、不发 PUT。创建若返回状态 0 或 ≥500（结果未知），按 URL 扫描绑定已有 `_id`，不重复创建。待推条数超过 `max(20, 向上取整(行数/2))` 且未带 `confirm` 时 409 `raindrop_push_confirm_required`。每 20 次远端请求停 1 秒。成功后的基线是**行自身字段的规范化快照**，用来吸收服务端归一。每次推送（成功或失败）写一条 `raindrop_sync_runs`。
- 拉取侧基线修正（否则推送会把没改过的行再推一遍）：无变化的跳过分支不再用远端快照覆盖账本基线；有远端变化的更新分支把基线记成**合并后写进行里的字段**，不是远端原样。两边相对基线都变、但行内容已经等于远端时，当作回声收敛，不报冲突。
- 路由 `POST /api/raindrop/push/preview` 与 `POST /api/raindrop/push`（body `{confirm}`）。开关关闭时与拉取一样 409。
- 设置页 `RaindropPanel`：预览列出将创建/将更新（差异字段中文名）/远端已消失；超过熔断阈值必须勾选确认后才能「确认推送到 Raindrop」。

**验证**：worker 74/74（阶段 A 的 68 例之上新增 `planPush` 分类、`diffFieldKeys` 口径、熔断阈值、创建+diff-only 更新、回读漂移不覆盖、创建响应丢失按 URL 绑定、远端消失行推送跳过）；web 44/44 保持。`pnpm build` 与 `pnpm typecheck` 随 0.1.3 → 0.1.4 一并通过。未做真实 Raindrop 账号演练。
