- **状态**：技术可行；阶段二第一版实施中
- **确认范围**：负责人确认收藏目标支持普通文档和多维表格，且可能优先使用多维表格；收藏属性参考 Raindrop，后续从 Menote 表格推送收藏到 Raindrop。
- **设计依据**：[TP3 开发计划](20261101-TP3-开发计划.md)、[TP3 MCP 剪藏服务设计](20261101-TP3-MCP剪藏服务设计.md)、[TP2 多维表格说明](../20261101-TP2-多维表格/20261101-TP2-多维表格.md)、[Raindrop Raindrops API](https://developer.raindrop.io/v1/raindrops)、[Raindrop 单条收藏 API](https://developer.raindrop.io/v1/raindrops/single)。

## 1. 可行性结论

技术上可实现，采集时间也可随表格记录推送并写入 Raindrop 的 `created` 字段。Raindrop 官方 API 将 `created` 列为收藏对象字段，并允许创建及更新单条收藏时传入该字段。接口文档确认可提交时间值；展示层最终如何呈现应在接入时用真实账号验证。

建议首版将收藏数据落到一份由用户指定的 Menote 文档或表格；用户偏好表格时，以表格作为后续 Raindrop 推送的主要数据源。收藏仍与网页剪藏分开：收藏追加元数据记录，剪藏正文进入收件箱。

## 2. 统一收藏字段

先采用可映射到 Raindrop 的基础字段：

| Menote 字段 | 类型建议 | Raindrop 映射 | 备注 |
| --- | --- | --- | --- |
| 标题 | 文本 | `title` | 页面标题，可编辑 |
| 网址 | 链接 | `link` | 收藏的规范目标 URL |
| 摘要 | 多行文本/文本 | `excerpt` | 页面描述，可空 |
| 备注 | 多行文本/文本 | `note` | 用户笔记，可空 |
| 标签 | 多选 | `tags` | Raindrop 字符串数组 |
| 类型 | 单选/文本 | `type` | Raindrop 允许 link/article/image/video/document/audio；本地可保留原值 |
| 封面 | 链接 | `cover` | 可选页面封面 URL |
| 采集时间 | 日期 | `created` | Menote 记录的采集时刻，推送时作为 Raindrop 创建时间 |
| 重要 | 复选框 | `important` | 对应 Raindrop 收藏标记 |

扩展抓取时能稳定取得的页面信息用于默认值；用户可在表格内补充或修订。诸如 Raindrop `_id`、同步时间、同步方向和冲突状态属于连接器关联状态，宜放在 Menote 的连接器元数据中，而非要求浏览器插件伪造或暴露为普通内容字段。具体存储位置需在 Raindrop 连接器设计阶段遵循主文档既有决策。

## 3. 两类存储目标

### 多维表格

- 表格文档以 YAML `fields:` 描述列定义，正文以标准 GFM 表格保存数据；现有字段类型包含文本、数字、日期、单选、多选、复选框、链接等，足以表达上表的首批属性。
- 设置时接收目标文件链接或 Item ID，由服务端确认目标归属、可写权限和明文类型；若为表格则新增一行。
- 目标表已具备列时按字段映射写入；缺少列时自动补齐首批标准字段定义和单元格，并遵从现有 Markdown 表格序列化和同步写入路径。
- 同一 URL 可以重复收藏；每次收藏由客户端生成 UUID 操作 ID，服务端通过现有同步操作幂等记录消除请求重试副本。

### 普通文档

- 在指定 Note 中按固定 Markdown 记录格式追加一条收藏，包含同一组语义字段。
- 必须避免将任意文本拼成不合法或不安全的 Markdown/YAML；URL、标题、标签等需按既定格式转义。
- 文档格式对人可读，但后续同步比表格更依赖严格解析和稳定格式，因此文档模式适合作为兼容目标，表格模式更适合作为 Raindrop 合流数据源。

## 4. MCP 权限与写入边界

现有 MCP 权限包括 `content:read`、`item:create`、`item:edit` 等；当前剪藏工具创建收件箱 Note，没有“对一个用户指定目标追加收藏”的专用工具。若收藏允许关闭内容读取，不能简单把 `content:read` 作为前提，也不应把目标文档正文返回插件。

推荐新增窄权限/专用工具，例如 `bookmark:write` 与 `append_bookmark`：

1. 请求只携带用户指定的目标 Item ID、收藏字段和幂等操作 ID。
2. 服务端内部验证目标属于当前用户、范围允许、目标未加密且类型为 Note 或 Table，然后读取并更新目标内容。
3. 服务端只返回成功/失败、目标 ID、行/条目标识等最小回执，不返回目标已有正文或其他项目内容。
4. 同一个已配置 MCP Token 可动态授予该权限；读取权限仍可关闭。令牌是否必须另行配置目标 ID 白名单，需在实现设计时和现有 scope 模型一起定稿。
5. 更新必须经过现有同步服务/操作契约，正确推进 rev、同步日志及冲突处理；并发编辑冲突应拒绝或生成可恢复的冲突结果，不能静默覆盖。

这是与“读取权限关闭但允许向指定文档追加”的目标相容的方式。若复用通用 `item:edit`，授权面过宽，也难以把 MCP 限制在用户配置的单一收藏目标。

## 5. Raindrop 推送路径

可复用主文档已经确定的服务端 Raindrop 连接器方向：绑定一张 Menote 表格与 Raindrop 账号/收藏范围，配置字段映射，读取表格记录并调用 Raindrop 单条收藏创建或更新接口；推送时把表格采集时间映射到 `created`。Raindrop 返回的 `_id` 需与 Menote 稳定行 ID 关联，用于后续更新和重复识别，不能仅凭 URL 作为身份。

后续实施需处理：

- OAuth/访问令牌的安全授权与加密存储；
- Raindrop `collection` 选择及字段映射；
- 远端 `_id` 与本地行 ID 的稳定关联；
- 首次推送、重复推送、远端已存在 URL 和部分失败的幂等行为；
- 本地与远端同时编辑的差异预览/冲突策略；
- Raindrop 对指定 `created` 值的真实账号集成验证。

本阶段实现浏览器写入 Menote，不实现 Raindrop OAuth、连接器或双向同步。此前需求与主文档将“扩展收藏写独立 Note”和“Raindrop 数据使用绑定表格”分开；负责人后续明确确认收藏也支持表格并用于未来推送。本次已同步修订需求说明书 v1.20、主文档 v0.18、TP3 计划与 MCP Token 权限 UI。
