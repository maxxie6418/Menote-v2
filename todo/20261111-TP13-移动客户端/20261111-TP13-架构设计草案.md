- **任务包**：TP13（编号原属 2026-11-08 代码审计修复，已并入 TP11 后释放）
- **创建日期**：2026-11-11
- **状态**：草案，待负责人确认 §11 五项后定稿
- **定稿去向**：结论并入 `wiki/Menote_V2_工程结构与组件设计`（升版）并同步 `AGENTS.md`
- **决策背景**（负责人确认）：
  1. 移动客户端重写（不走套壳），Expo + React Native，覆盖 Android 与 iOS；
  2. 移动端与 web 端**功能大体一致、内容严格一致**，但设计重心不同：移动端偏灵敏、快速、方便（速记、快览、采集），web/桌面偏内容编辑、阅读与思考；
  3. 编辑器形态未定：理想是复用桌面结构并精简，编辑方式可能按移动端特色重新设计，不绝对照搬；
  4. **不排除后台同步**：分享进入 App 的内容应在后台完成上传，而非等待用户打开应用；
  5. 开发工作量可接受，倾向两线分别打磨；移动端发版频率低于 web。

## 1. 核心架构决策

### 1.1 一句话

**把领域核心（同步、加密、内容格式）从 `src/web` 中抽离为独立包 `src/core`，web 与 mobile 各自实现平台适配器，契约与规范单源于 `src/shared`，Worker 保持唯一服务端出口。**

这是 ports & adapters（六边形）结构的落地：领域逻辑不感知平台，平台差异全部收敛在适配器层。

### 1.2 四条产品约束与架构的对应关系

| 负责人约束 | 架构落点 |
| --- | --- |
| 功能大体一致 | 领域逻辑（同步/加密/内容操作）单源于 `core`，两端 import 同一份实现 |
| 内容严格一致 | 内容格式与版本规范进 `shared`；两端编辑器实现自由，但读写同一格式 |
| 体验分叉、两线打磨 | UI 层与平台适配器完全分属 `web` / `mobile` 两包，互不引用 |
| 不排除后台同步 | `core` 为纯 TS、无平台 API、不依赖 UI 生命周期，可在后台任务运行时执行 |

关键推论：**"内容一致"的保障不靠约束人，靠"内容格式只有一份定义"**。编辑器无论两端差异多大，都是同一格式之上的两种实现。

## 2. 包结构

```
src/
├─ shared/     契约与规范（无逻辑）
│   ├─ types / contracts     既有 API 与数据类型（现役，扩充）
│   ├─ migrations/           数据库迁移声明（单源，新增，见 §5）
│   ├─ crypto-spec/          加密格式规范 + 测试向量（新增，见 §6）
│   └─ capture/              CapturePayloadV1 采集载荷契约（新增）
├─ core/      领域核心（新包 @menote/core，纯 TS）
│   ├─ sync/                 同步状态机（自 web/syncEngine 抽离）
│   ├─ keyring/              密钥环状态机（解锁/锁定/超时）
│   ├─ content/              内容格式操作与版本迁移
│   └─ ports/                Storage / Crypto / Transport / Clock / Log / Lock 接口定义
├─ web/       现有前端（UI + web 适配器）
│   ├─ features / components UI（不动）
│   ├─ services/             薄编排层，调用 core
│   └─ adapters/             Dexie、WebCrypto、WebLocks、BroadcastChannel、fetch
├─ mobile/    移动客户端（新包 @menote/mobile，Expo + RN）
│   ├─ app/                  Expo 入口、路由、原生壳配置（prebuild）
│   ├─ ui/                   九屏界面（按 wiki/Menote_V2_移动端设计_v0.1.md）
│   ├─ services/             薄编排层，与 web 同构
│   └─ adapters/             expo-sqlite、原生加密桥、分享、后台任务、文件系统
└─ worker/    服务端（结构不变，职责扩充，见 §7）
```

分层纪律沿用 `AGENTS.md` 并扩展为：**UI → services → core → 适配器 → 平台能力**。

- `core` 禁止 import 任何 `web` / `mobile` / `worker` 的代码，禁止出现 `window` / `document` / `navigator` / `Dexie` 等平台标识；
- `web` 与 `mobile` 互相禁止 import（不含通过 `shared`/`core` 的间接共享）；
- worker 侧 SQL 仍在 `worker/db`，`shared/migrations` 是**客户端本地库**的迁移声明，与 D1 迁移是两套（服务端 schema 与客户端缓存 schema 本就不同构）。

## 3. core：领域核心

### 3.1 ports（接口）

```ts
interface StoragePort {
  // outbox 与实体读写，两端各自实现（Dexie / expo-sqlite）
  listPendingOutbox(limit: number): Promise<OutboxRow[]>;
  applyRemote(items: RemoteItemBatch): Promise<void>;
  settleOutbox(ids: string[], result: SettleResult): Promise<void>;
  getCursor() / setCursor(cursor: string): Promise<void>;
}
interface CryptoPort {
  deriveKek(password: string, salt: Bytes, iterations: number): Promise<Bytes>;
  seal(key: Bytes, plaintext: Bytes, aad?: Bytes): Promise<SealedBox>;
  open(key: Bytes, box: SealedBox, aad?: Bytes): Promise<Bytes>;
}
interface TransportPort { call(api: ApiCall): Promise<ApiResponse>; }  // cookie 或 token 差异在此消化
interface LockPort { withLock(name: string, fn: () => Promise<void>): Promise<void>; }  // WebLocks / 进程内 mutex
interface ClockPort { now(): number; }
interface LogPort { ... }
```

### 3.2 同步状态机

现状 `syncEngine.ts`（456 行）的单轮 = 推送排水 + 拉取推进，抽为纯函数：

```
输入：当前游标 + outbox 快照 + 远端分页响应
输出：待执行的数据变更序列 + 新游标 + 下一批指令 + 诊断事件
```

适配器负责实际读写与网络；**重试退避（1/2/4/8s…封顶 60s ±20%）、rejected 不阻塞队列等既有语义原样保留**，抽离过程以 web 测试全绿为验收，不改变行为。

多标签单同步者（Web Locks）留在 web 适配器；mobile 前台为单进程，LockPort 退化为进程内 mutex；mobile 后台任务与前台不并发的保证由平台任务调度承担。

### 3.3 keyring 状态机

解锁 → 就绪 → 超时/手动锁定 的状态迁移进 `core`；KEK 在内存的持有方式、超时策略单源。web 用主密码解锁，mobile 用生物识别解锁（KEK 由 Keystore/Keychain 包裹）——**两者对 core 而言是同一个状态机**，只是解锁指令的来源不同。

## 4. 认证：双通道

- **web 保留 cookie 会话**（现役 `sessions` 表 + SameSite=Strict + Origin 校验，不动）；
- **mobile 走 token 通道**：新增设备令牌表（userId、deviceId、tokenHash、refreshChain、lastSeenAt、revokedAt），Bearer 头认证，支持吊销与设备列表管理；
- 两通道共享 user 主体与权限判定；worker 中间件按通道分别解析，后续授权逻辑一致；
- 失败与过期语义、离线时的本地降级策略在 `shared/contracts` 定义。

## 5. 数据层单源策略（待负责人选型）

三个可选方案，**推荐 C**：

| 方案 | 做法 | 收益 | 风险 |
| --- | --- | --- | --- |
| A. web 也迁 SQLite（wa-sqlite/OPFS） | 两端同构，真正单源 | 存储主权、事务一致 | 推翻 Dexie + liveQuery 生态，web 重构面大 |
| B. 双轨各自维护 schema | 现状延伸，改动最小 | 零迁移成本 | 字段含义漂移，靠人盯 |
| **C. 声明式 schema 单源（推荐）** | `shared/migrations/` 放声明式表结构（TS 定义），两端生成 Dexie schema 与 SQLite DDL；配 roundtrip 契约测试 | 单源且不动 web 存储 | 需写一次生成器（一次性成本，量小） |

C 方案要点：同一组测试数据在两端各跑一遍读写 roundtrip，断言字节级一致；**schema 变更只允许改声明源**，两端生成的产物不许手改。

## 6. 加密体系

- **格式规范**（`shared/crypto-spec`）：KDF 参数结构（算法、hash、盐、迭代数）、KeyWrap 封套结构、密文封箱（IV 长度、AAD 构成、base64 变体）逐字段定义，附 JSON 测试向量；
- **实现**：web = WebCrypto（现役 `cryptoService` 的行为不变）；mobile = 原生桥（CryptoKit/CommonCrypto PBKDF2 + AES-GCM，或 `react-native-quick-crypto`，实现选型在 mobile 骨架阶段定）；
- **验收**：两端跑同一组测试向量，全部通过才算实现合格——这是"内容一致"在加密维度的机械门禁；
- 主密码/恢复码不落任何存储与日志的红线不变；mobile 生物识别解锁只包裹 KEK，不改变密钥派生格式。

## 7. worker 端调整

1. **客户端版本门槛**：请求头 `X-Client-Version`（platform + appVersion），worker 返回 `minSupported`；低于门槛返回 426 + 升级指令。web 从第一天起也带此头（成本为零，约束一致）；
2. **API v1 契约冻结**：`shared/contracts` 扩充为完整请求/响应 schema，破坏性变更须升版本号并保留兼容窗口（覆盖 N-2 个 App 版本）；
3. token 认证通道（§4）；
4. 采集载荷 `CapturePayloadV1` 入口（§8）。

### 7.1 服务端可移植性：双部署目标（Cloudflare Workers 为主，Docker/自托管为镜像备份版）

**约束（负责人 2026-11-11 补充）**：功能稳定后可能部署在自有服务器或 Docker 上，作为 Cloudflare Worker 的镜像备份版本，**底层不得写死**。

现状勘查结论（2026-11-11）：耦合面小、有利条件充分——

- HTTP 层为 Hono，`app.fetch()` 可直接运行于 Bun/Node（上游 EdgeEver 即以此实现 Workers/Docker 双形态）；
- `index.ts` 47 行纯装配；db 层全部参数注入式签名（`f(db: D1Database, …)`），services 层不持有全局 env；
- D1 即 SQLite：SQL 方言同构，`worker/db/migrations/*.sql` **一套迁移文件服务两个部署目标**。

**设计**：服务端同样采用 ports & adapters，与客户端侧的 core/适配器模式对称——

| Cloudflare 绑定 | 服务端端口 | Docker/自托管实现 | 备注 |
| --- | --- | --- | --- |
| D1 | `SqlDb`（prepare/bind/all/first/run/batch 子集，含事务语义） | `@libsql/client`（async API 与 D1 近同构） | db 层签名从 `D1Database` 收窄为该接口 |
| R2 | `ObjectStore`（put/get/head/delete/list） | 本地目录 或 S3/MinIO | `AttachmentStoreContext.bucket` 同步收窄 |
| Queues（AI_TASKS） | `QueuePort`（enqueue） | 进程内入队 + 轮询扫 jobs 表 | 消费模型不同，是最难的适配点；jobs 表已存在 |
| Cron Triggers | `SchedulerHost` | node-cron / systemd timer | 调同一个 `dispatchScheduled` |
| Workers AI | `AiPort` | OpenAI 兼容 API / 本地模型 | aiService 收口到接口后 |
| Static Assets | — | 任意静态服务器 + SPA fallback | 前端产物同构，无代码耦合 |

- **双入口装配**：`index.ts`（ExportedHandler，CF）与新增 `server.ts`（Bun/Node），各自的适配器把绑定翻译为端口实现；路由、services、db、迁移 SQL 完全共享；
- **纪律（立即生效）**：services 层禁止直接读 `env.XXX` 绑定（现 `healthService`、`raindropService` 中的 `Reflect.get(env, …)` 属于待收口点），绑定访问只允许出现在装配层与适配器内；
- **数据可迁移**（镜像备份的另一半）：D1 → SQLite 走 `wrangler d1 export` 的 SQL dump 直接灌入；R2 → 文件/S3 走对象同步；既有的备份目标推送能力（`backupTargets`）作为现成的异地备份通道，镜像版可充当恢复目标；
- **对客户端的唯一要求**：API base URL 可配置（mobile 本就必须支持自部署地址输入；web 已隐含同源）。

**待确认**：镜像版的交付形态——仅作灾备恢复目标（数据可导入、可冷启动），还是要求与 CF 版双活可服务（需要数据双向同步方案，复杂度显著上升）。建议先做前者。

结构与既有 routes → services → db 三层不变。

## 8. 采集与后台（mobile 特有路径）

- **CapturePayloadV1**（`shared/capture`）：分享进入的标准载荷（kind: url / text / image / file，title、sourceApp、时间戳、内容引用）；
- **iOS**：Share Extension 独立进程 → 写 App Group 共享容器暂存区 → 主 App 前台启动时或后台任务中由 core 合并逻辑消费入 outbox；
- **Android**：分享 intent 直达主进程，直接入 outbox；
- **后台任务**（expo-background-task / WorkManager）：执行体 = `core` 同步状态机 + mobile 适配器；不承诺执行时机（由系统调度），承诺**打开即同步 + 后台尽力**；分享内容的后台上传以此为上限，若未来要求强及时性需引入推送，属后续决策；
- mobile bundle 严禁包含 `src/capture/upstream/edgeever/`（AGPL-3.0-only）代码；移动端网页提取走端内 WebView 自实现或服务端接口。
