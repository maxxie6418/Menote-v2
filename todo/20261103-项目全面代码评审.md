## 2. P0（会丢数据或不可逆损坏，均已核验）

### 2.1 网页端附件引用计数恒为 0

网页端创建条目时把 `attachmentHashes` 写成空数组，保存正文时也不从正文重新提取引用：

- `src/web/src/services/contentService.ts` 的 `createNote`、`createMemo` 创建条目时写 `attachmentHashes: []`；`src/web/src/services/privateSpaceService.ts` 创建私人空间笔记时也写空数组。`saveItemContentInner` 更新正文只保留当前字段，不调用 `extractAttachmentRefs`。
- `extractAttachmentRefs` 在 `src/web/src/services/attachmentService.ts`，被附件面板的「引用文章」列、zip 导出、断链提示及设置预取调用；这些调用均不在保存/入队路径。
- 服务端 `src/worker/src/services/syncService.ts` 用载荷里的 `attachmentHashes` 对齐引用，因此网页端新建并保存的附件引用计数恒为 0。MCP 剪藏会填写调用方提供的哈希；MCP `create_memo` 仍写空数组。

后果：

- `src/web/src/features/attachments/AttachmentListPanel.tsx` 的「一键清理」和单条删除均按服务端 `refCount === 0` 过滤。界面上「引用文章」是前端实时解析 markdown，可能显示有引用；清理/删除操作却仍可能把正在使用的网页端附件物理删除。
- 备份按 `attachment_hashes_json` 收集附件（`src/worker/src/db/backup.ts`），快照不含这些文件，恢复后图片全丢。
- 30 天自动清扫要求 `orphaned_at` 非空，这些行从未被 realign 触碰，自动清扫暂时不会误删。会引爆的是手动清理和备份。

修法：保存时用 `extractAttachmentRefs(markdown)` 回填 `attachmentHashes` 并写入同步载荷；备份改为「正文引用 ∪ 元数据表」。

**【已修复，0.1.25】**：正文保存路径（`saveItemContent`、形态切换、版本恢复、启用/保存/解密加密正文）改为按正文解析并回填 `attachmentHashes`，纯解析函数下沉到 `src/web/src/lib/attachmentRefs.ts`（`attachmentService` 仍从该处导出 `extractAttachmentRefs`）。备份侧原本就按 `attachment_hashes_json` 收集（`db/backup.ts`），列表补齐后备份自然收录，无需再改收集口径。服务端引用计数沿用载荷里的 `attachmentHashes`，随之恢复。MCP `create_memo` 仍写空数组（Memo 正文无附件引用，不影响计数）。

### 2.2 全量重同步只返回前 200 条，客户端先删本地

- `src/worker/src/services/syncService.ts` 的 `buildSyncPage`：游标早于保留窗口时调用 `readAllItemsPage(db, userId, 0, PULL_PAGE_LIMIT)`，offset 恒为 0，却返回 `hasMore: items.length === 200` 和 `nextCursor: oldestSeq - 1`。`readAllItemsPage` 按 `created_at` 升序，因此返回的是最早 200 条。
- `src/worker/src/db/sync.ts` 的 `readAllItemsPage` 支持 offset，调用方从未传入大于 0 的值。
- `src/web/src/services/syncEngine.ts` 的 `pullUpdates`：收到 `fullResync` 后，先删除本地所有不在 outbox pending 集合里的条目、主题、评论，再写入本页。主题与评论在服务端全量返回，不受条目分页限制。

触发：新设备游标为 0 且日志已被 90 天清理裁剪，或离线超过保留期。条目超过 200 条时，本地先被清空，只写回按 `created_at` 最早的 200 条；客户端会因 `hasMore` 再请求，但首屏游标设为 `oldestSeq - 1` 后，第二次请求已不再满足缺口条件，转为增量日志读取，不会翻到下一页。90 天内没改过的更晚条目不会再出现在 `sync_log` 里，本地永久缺失。服务端数据仍在。

修法：全量重同步使用独立分页参数，循环拉完；客户端确认快照完整后再按差集删除。

### 2.3 备份恢复把密钥包装写成垃圾

- `src/worker/src/db/keyWraps.ts` 以 BLOB 写入 `kdf_salt` / `iv` / `ciphertext`。
- 备份收集是 `SELECT *` 后 `JSON.stringify`。BLOB 运行时表示（例如 `Uint8Array` 或 `ArrayBuffer`）序列化为普通 JSON 值，恢复后不再是 `Uint8Array`。
- `src/worker/src/services/restoreService.ts` 的 `toB64`：非 `Uint8Array` 值走 `String(value)`；普通对象会变成 `"[object Object]"`，数组会变成逗号分隔字符串，再写回包装表，均不是原始密钥字节。`Uint8Array`、`ArrayBuffer` 或普通数组的 JSON 形态均不保留字节语义。
- `topic_key_wraps` 进了备份，恢复路径不读它。

后果：将该备份导入恢复后，单篇加密条目的包装块会被无效字节替换，相关条目无法解锁；当前 Web 界面尚无备份导入入口，实际触发需调用恢复接口。明文条目的正文存于 `content_markdown`，其 `content_ciphertext` 为 `NULL`；本问题针对 BLOB 密钥包装，不是正文列的文本序列化。

修法：收集备份时把 BLOB 显式编成 base64；恢复端对非法编码拒绝而不是静默转码；补上 `topic_key_wraps`（并核对设置等 manifest 数据的恢复契约）；加一条加密条目备份往返测试。

## 3. P1（功能错误或静默分歧）

同步：

- `src/worker/src/services/syncService.ts` 的单操作应用异常会收成 `rejected`。客户端对条目/主题/评论的 `rejected` 标 `Number.MAX_SAFE_INTEGER`，不再自动重试；业务拒绝或应用阶段的存储故障都可能让该操作死信，本地已保存而其他设备收不到。设置类 rejected 会由同步流程放行重试，故不适用「永不重试」。整组写入在应用开始前失败时，则不能据此断言已被标记死信。
- 同一次 item upsert 的写行、包装块、`sync_log`、幂等记录、附件对齐是多次独立 SQL，没有 `db.batch`。中途失败会留下「行已更新、日志没有」。
- `src/web/src/db/itemsRepo.ts` 的 `bulkPutItems` 不比较 `rev`。全量重同步或增量页恰好包含同一条目时，拉取可能用服务端版本覆盖本地版本；纯本地且未出现在拉取页中的条目不会因此被覆盖。outbox 载荷保存入队时的条目快照，仍待推送的内容可能随后再上传。
- 幂等重放时，已记录的 `rejected` 会被返回成 `duplicate`，客户端按成功处理；需重放相同 `operationId` 才触发此问题，未记录的服务端异常不会走该路径。
- `SYNC_CURSOR_KEY = "syncCursor"` 是全局单键；登出只调接口，不清 IndexedDB。同浏览器换账号会沿用前一账号的游标，可能跳过或错位新账号的同步日志；服务端仍按当前会话用户过滤，不会因此直接拉取前一账号的数据。评审未核验本地条目、包装块等数据在换账号时的隔离/清理行为，不据此推断为安全隔离。
- 【已修复，64832d0】AI 设置入队 key 为 `ai`，服务端 `applySetting` 曾只接受 `appearance`，导致设置无法同步；当前 `ORDINARY_SETTING_KEYS` 已包含 `ai`。待处理 outbox 时本机跳过拉取应用仍是保护行为，不应再表述为此缺陷的持续后果。
- 加密条目冲突不留副本（`saveConflictCopy` 对非 plain 直接返回），后推的编辑被静默丢掉。明文条目有副本。冲突副本本身不入 outbox，触发下一次全量重同步时会被清掉。**【已修复，0.1.24/0.1.25】**：冲突副本现在连同密钥包装块一并入队上传（不再只落本地），加密条目也留副本；副本新增 `conflictOf` 字段记录与原条目的关联（迁移 0037），文档区给出「打开原条目」入口；同批重复冲突仍只保留最新本地稿一份。
- 恢复旧备份时 `rev` 取较大值，内容字段无条件用备份行覆盖，版本号与正文不再对应；更新还未同步覆盖加密标志字段，旧行标志可能与备份正文不一致。

加密与前端：

- `src/web/src/services/keyringService.ts` 的 `touchActivity()` 没有任何调用方。15 分钟锁定实际是最近一次会话密钥状态变化后的超时，并非用户活动超时；锁定替换编辑器时，最后一次防抖窗口内的输入会被丢弃。
- `src/web/src/features/notes/EncryptedNoteView.tsx` 在解锁后对 `readPlain` 的 `null`（解密失败）使用 `?? ""`。空串会进入自动保存，用「加密的空串」覆盖原密文。解除加密按钮可在明文尚未读完时确认，会把整篇转成空明文。界面无解密失败提示；自动保存是否留版本取决于版本封存条件，解除加密路径不封存，不能保证旧版可恢复。
- 加密笔记可以上传附件，`attachmentService` 把文件明文 POST 到 R2。需求 FR-ENC-5 要求附件始终密文。M2 管理线记录既未声称完成，也未列为遗留；管理线计划曾列「密文入 R2」，计划与实际记录/实现需区分。
- `encryptionCommandService` 的启用加密与解除加密绕过 `enqueueWrite`。与自动保存交错时，可能把刚加密的内容再推成明文，或反过来。
- `src/web/src/services/versionService.ts` 永久删除的网络失败被 `.catch(() => {})` 吞掉。本地已硬删，服务端软删行仍在；若软删日志仍在当前游标之后，或之后触发全量重同步，条目可能重新出现在本地，不是每次增量同步都会拉回。
- 回收站条目软删后，唯一附件引用归零并进入 30 天孤儿观察期；定时清理运行且孤儿期满后会物理删除附件，而条目软删记录保留 90 天。此后恢复条目时不会重传附件，恢复窗口内可能出现附件 404（确切时间取决于定时任务执行及共享引用情况）。

安全口径（需负责人裁定，不是已证实的漏洞）：

- `sessions.id` 存的是 cookie 原值（`src/worker/src/db/auth.ts`）。密码、MCP token、备份凭据、Cloudflare token 都做了哈希或密封，会话凭证没有。若「登录密钥不明文入库」包含会话令牌，可评估存储 SHA-256 摘要并调整查找协议；若不包含，应在纪律或开发记录里写明。

抽样核查未发现上述资源访问路径的直接越权，但不构成全面安全证明：已检查的附件、同步、回收站、备份、恢复、AI 任务、MCP token、监控及剪藏模板查询按用户隔离；抽查的 MCP 读 SQL 排除加密条目与私人空间。会话 cookie 为 HttpOnly + Secure + SameSite=Strict；抽查的变更路由有同源守卫，但同源中间件仅在请求带 Origin 时比对，缺少 Origin 时不阻断。仍需逐项审查 MCP 写路径、监控采样及备份查询，并核对 sync item upsert 的冲突更新用户边界。

## 4. P2（精选，不阻塞）

- cron 入口对 `AUTH_PEPPER` 只做类型强转，缺失时靠下游解密失败兜底，与路由层显式 503 不一致。当前效果仍是失败关闭。
- AI 队列 `max_retries: 3` 与代码里 `attempts < 3` 组合，实际比重试配置少一次。
- 恢复导入 `slice(0, 5000)` 静默截断，响应不报 skipped。
- 空白草稿注释写「种子永不上传」，实现会在约 300ms 后的自动同步里推走；24 小时后本地删除且不发墓碑，其他设备留下无标题条目。
- `upsertTopicRow` 冲突时不更新 `parent_id` / `depth` / `is_enc_space`。当前 UI 不能移动主题，尚未爆发。
- 附件先写 R2 再写 D1，D1 失败会留下无元数据对象，清理任务扫不到。
- `cryptoService.toB64` 用展开运算符，超长正文（大约超过 100KB）加密可能 `RangeError`。
- `EncryptSetupDialog` 确认路径无 try/catch，异常时按钮永久忙碌。
- 源码与所见即所得切换不先 flush，可能丢掉 800ms 内的输入。编辑/预览切换有 flush。
- 开放注册与附件上传无限流。登录有节流。
